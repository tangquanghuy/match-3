# SillyTavern 与三消项目的实际接入边界调研

状态：接入前调研修订版

当前产品方向、协议字段、存档归属和交付顺序见 [通用战斗产品与实施方案](sillytavern-battle-product-plan.md)。本文保留现有代码事实和调研依据；下文早期示例不作为已实现接口或最终产品规格。

## 核心补充：敌人组装器的实际基础与产品边界

当前决定：运行时 AI 提供法力颜色、稀有度（杂兵/精锐/首领/领主/传奇）、形态（人形/野兽/类人/怪物/异形体）与项目已有队伍职责，共同查找立绘。先完成这层，再设计特质和技能规则。产品契约见 [产品方案](sillytavern-battle-product-plan.md)，实际标签与查询见 [立绘形态标注](portrait-forms.md)。

人脸与人形身体归人形，兽耳、尾巴、角不使其成为类人；类人的脸明确为非人面孔。旧提示词写兽族，不等于成图有兽面。只有形态新增视觉标注，颜色、稀有度和职责直接读取现有数据；不另造职责适配标签。

### 1. 立绘、族群与战斗身份分别绑定

src/data/troops.json 与现有部队图库各有 1800 项。原生 battleBridge.ts 写入 templateId 和 portraitUrl，渲染器可直接消费快照中的 portraitUrl。通用敌人单独保存蓝图和图片绑定，不通过技能或名字反查原生部队并带回原身份。

原有 troopTypes 混有种族、职业和特殊身份，其联动依赖需要后续独立适配。形态分类不等于族群身份。叙事名称、具体种族、具体职业和外观正文留在酒馆；源名称、王国和原始跑图文本只在离线整理时使用。

本轮已按成图完成 1800 项粗粒度归类，原类人候选另做面部专项复查，累计 90 项放大复核。四维索引有 1092 个非空组合，可精确查询和导出可用组合；尚未接进战斗准备页或替代技能组装器。

### 2. 当前技能组合器不能覆盖两千多技能

`src/session/assigner.ts` 现在只是一个补空字段的分拣器：杂兵池只有 `7004`，精英池为 `7132/7004`，首领池为 `7155/7132`，领主池为 `7062/7155`，传奇池为 `7063/7062`，特质也来自少量硬编码池。它按 `tier + troopTypes + externalId` 做确定性选取，不能依据 AI 的职业、主题、目标形状、控制时长或技能复杂度组合敌人。因此它不是“完整技能组合器”，不能直接承担通用敌人设计。

同时，项目并不是只有这几个技能。当前数据有 1800 个部队条目、1795 个不同的部队技能 ID、718 把武器；`artifacts/spell-build.txt` 的当前覆盖报告记录 1816 个技能条目，其中 1811 个已有编译原型。这里的“已编译”只表示有 `SkillPrototype` 可注册和执行，不表示每个官方语义都完全相同；技能库仍有特殊宝石、位置操作、任意状态、复杂跨段目标和部分数值来源等受限语义。`fallbackPrototype()` 只能保证扣法力后继续运行，不能作为 AI 设计的有效技能。

所以要区分两种覆盖：

1. **原子技能覆盖**：已有的 `skillId + SkillPrototype` 整体作为一个能力候选。已编译原型全部进入适配索引，但只有通过通用依赖检查的项目才能进入可选池；部分实现必须标注限制，固定族群、召唤等依赖必须先绑定或适配。
2. **组合原语覆盖**：新敌人需要动态生成能力时，只允许从经过验证的原语模板生成，例如 damage、heal/shield、buff/debuff、status、cleanse/dispel，以及已适配的有限 gem 操作。`summon`、`transformTroop`、`devour`、`oneOf/choose`、经济效果、站位操作、依赖特殊宝石或跨段随机目标绑定的技能，不能仅因已有原型就直接开放；须逐类通过通用适配，并分别声明是否允许组合。

这意味着不需要重写两千多个技能，也不能宣称一个自由组合器能合理覆盖所有技能。方案是“全量适配索引 + 已适配原子库 + 受限组合器”：复杂技能逐类适配，安全机制才可组合；无法验证的机制不进入候选池，不能用空原型或降级效果冒充。

### 3. 必须重新建立技能索引，但打标应自动化

`src/data/weapon-skill-meta.json` 目前主要是武器技能保真度和缺失特性登记，不足以支持敌人检索。需要新增构建产物 `skill-index.json`（或等价的 TypeScript 生成模块），每个条目至少包含：

```json
{
  "skillId": "7132",
  "mode": "atomic",
  "mechanicTags": ["damage", "splash"],
  "targetTags": ["single-enemy"],
  "shapeTags": ["adjacent"],
  "statusTags": [],
  "colorTags": ["Red"],
  "roleTags": ["Striker"],
  "complexity": 2,
  "rarityRange": ["杂兵", "精锐"],
  "supportsComposition": false,
  "fidelity": "full",
  "unsupportedFeatures": []
}
```

标签生成顺序应是：

1. 直接遍历 `SkillPrototype.segments`，从 `kind`、target、range、status、颜色和分支结构自动提取；
2. 从部队/武器目录补充 manaColors、manaCost、role、稀有度和等级范围；
3. 用现有描述文本和 `weapon-skill-meta.json` 补充机制名、保真度和缺失特性；
4. 只对自动识别不了的条目人工审核，并输出 `unclassified` 清单和覆盖率；
5. 每次技能库变更都重新生成索引并运行 smoke/回归测试。

需要重新打标，但不是把两千多个技能手工重写一遍。自动标注负责规模，人工审核负责歧义；没有索引覆盖率和未分类清单，就不能让 AI 依赖这套技能库。

### 4. 敌人设计器应是预算编译器

敌人设计器的输入和输出应固定为以下契约：

```text
EnemyDesign
  → validateDesign（法力颜色/稀有度/五形态/现有职责，后续扩展特性与关系）
  → resolvePresentation（四维严格相交 → 本地真实图候选 → portraitUrl）
  → querySkillIndex（职责/目标/机制/通用适配状态过滤，绑定族群与阵营关系）
  → budgetCheck（技能数量、复杂度、伤害、控制持续时间、召唤数、资源消耗）
  → resolveStats（level/rank/职责/耐久倾向 → 四维数值）
  → buildCombatantSnapshot
```

当前角色只有一个主动 `skillId`。首版每个对象使用一个完整主动技能，威胁档位提升可增加段数、被动和联动成本，不能把“首领两个独立技能槽”当作已有能力。预算检查目标数量、控制回合、召唤上限、伤害上限和 `manaCost`，不能只按稀有度抽签。候选为空时明确报错；只有显式可选的偏好允许降级，不能静默替换必选机制，也不能把 AI 的自然语言描述直接塞进 `skillId`。

魂片来源由宿主在接受敌人设计后建立内部蓝图记录，而不是按名字、立绘或源项目族群直接合并。蓝图保存能力和展示绑定，进度记录由程序维护；运行时 AI 不提交对象 ID 或蓝图 ID，也不从自由文本猜物种。最终规则见产品方案第 5 节。

### 5. 这套方案怎样保持一个项目

同仓库新增通用战斗层与 `src/integrations/sillytavern/` 宿主适配层，不复制三消项目。通用层管理语义设计词表、关系绑定、技能索引、预算和图片解析；宿主层处理变量、存档与报告。引擎继续接收编译后的 `BattleRequest`，原生模式保留自己的 `troopId/kingdom/role` 路径；固定身份依赖的通用变体必须适配执行逻辑，不能仅靠接口隔离。建议结构见产品方案第 11 节。

交付顺序统一为：立绘四维筛选 → 特质/技能及族群底座 → 敌人组装预览台 → 真实酒馆战斗闭环 → 魂片与淬炼 → 高级机制与萃取。宿主能力探针可独立验证；真实立绘不推迟到可选皮肤阶段。已有 `assigner.ts` 保留兼容用途，通用编译器显式给出技能与被动，不走其固定种族补全路径。

先记录一个纠正：之前的文档把 SillyTavern AIRP 的 `技能树`、`资源技能`、`特质`当成了三消项目的养成数据源，这是错误的。它们只服务于酒馆里的 DND/AIRP 运行时。当前三消项目自己的武器、技能、法力颜色、部队等级和淬炼都有独立数据与代码路径，不能通过复用这些 ST 字段来“拼接”。

本调研只讨论实际存在的两套系统如何通过适配层连接：

```text
ST AIRP 变量（叙事角色、DND 属性、文字装备）
        │ 只交换少量稳定代码和战斗快照
        ▼
SillyTavern 适配层 / bridgeState
        │ 按代码查三消目录，生成 BattleRequest
        ▼
三消项目（武器原型、法力、棋盘、部队、敌人、结算）
```

推荐结论：酒馆侧只保存一个稳定的武器代码；武器技能、法力颜色、法力消耗、淬炼上限和展示信息全部由三消目录按代码派生。AI 可以注册一件叙事武器，但不能自行填写三消技能和颜色，也不能把三消技能写入 ST 的 `资源技能` 或 `技能树`。

## 1. `docs/酒馆变量` 的真实模型

`docs/酒馆变量`才是当前酒馆角色卡的实际变量约束。它明确了以下事实：

- `人物/等级`、`人物/生命值上限`、`人物/AC`、六维属性和部分战斗属性是外部脚本维护的只读或半只读字段。
- `人物/技能树`、`人物/主动技能槽`、`人物/觉醒技能槽`、`人物/资源技能`、`人物/特质`、`人物/状态效果`属于 AIRP/DND 运行时。
- `羁绊列表`中的技能也是文字冒险队友技能，字段是品质、类型、效果和描述，没有三消 `troopId`、法力色或棋盘技能 ID。
- `人物/装备列表`是叙事装备记录，当前字段包括 `类型`、`部位`、`装备箱`、`名称`、`品质`、`标签`、`等级`、`属性加成`、`效果`和`描述`。没有三消武器代码、技能原型 ID 或法力颜色。
- `人物/背包/道具`是叙事道具，规则明确禁止把可穿戴装备塞入道具；不能直接拿它当三消材料仓库。
- `战斗/是否战斗中`和`战斗/当前轮次`描述的是 AIRP 回合战斗生命周期，不等于三消棋盘是否正在运行。
- `等级`和`AC`不能由 AI 直接改；经验使用 `本级经验`增量，升级由辅助脚本处理。

文件还规定了严格的变量更新语义：`add`必须建立完整对象，数字增减使用 `delta`，更新使用 `replace`，装备穿脱只改 `装备箱`，技能使用更新冷却。接入不能把一份大 JSON 结果直接覆盖到 ST 变量里，必须产生有限的白名单补丁。

### 1.1 ST 侧可直接作为输入的字段

以下数据可以作为桥接输入，但它们仍然是 AIRP 数据，不是三消数据：

| ST 路径 | 可提供的信息 | 接入方式 |
| --- | --- | --- |
| `/人物/名称`、`种族`、`职业`、`背景设定` | 显示名和叙事标签 | 仅进入快照显示/标签 |
| `/人物/等级`、`本级经验` | DND 等级和奖励回填锚点 | 读取；经验只通过白名单 delta 写回 |
| `/人物/属性/*` | 六维属性 | 用于桥接系数或报告，不直接等同三消四维 |
| `/人物/当前生命值`、`临时生命值` | 入场残血和护盾 | 读取；结算后按实际结果写回 |
| `/人物/装备列表` | 文字装备身份和描述 | 读取；三消能力只读取关联武器代码 |
| `/羁绊列表/*` | 固定同行角色 | 读取角色 ID、等级、HP和叙事信息 |
| `/世界信息/位置`、`当前事件` | 遭遇地点和剧情触发 | 转成位置/环境标签 |
| `/系统配置/战斗数值模式` | 原生 DND 或新模式选择 | 作为桥接模式开关 |

以下内容不能作为三消技能输入：

- ST `资源技能`对象的品质、次数和文字效果；
- ST `技能树`的技能阶位和技能槽；
- ST `特质`和职业特质；
- ST `羁绊列表/*/技能`中的文字技能；
- AI 自己写进装备 `效果`里的三消伤害倍率、法力颜色或掉落规则。

它们可以继续服务于 AIRP 叙事，但不能被三消引擎当成已注册的可执行技能。需要让三消能力进入酒馆提示词时，应由适配器生成只读的“武器桥接面板”，而不是把它们伪装成 ST 资源技能。

## 2. 三消项目当前的实际做法

### 2.1 玩家武器不是 ST 装备对象

三消项目的主角武器来自 `src/data/weapons.json` 和 `src/meta/data/weaponCatalog.ts`：

- 目录目前有 **718 把**武器，代码格式是 `gw_<referenceName>`。
- 每个目录项包含 `rarity`、`rarityIdx`、`weaponType`、`manaColors`、`manaCost`、技能名称、技能描述、技能原型、词缀和获取条件。
- `weaponCatalog.ts`会把目录行编译成 `WeaponDef`，并通过 `spellId`从已编译的 `SkillPrototype`集合中取得实际战斗技能。
- `CATALOG_WEAPONS`只包含有可执行原型的武器；没有原型的目录占位项只能浏览，不能装备。
- `anyWeaponById()`负责把 `gw_*`代码解析成目录武器；旧的 `w_*`代码只通过迁移映射到 `gw_*`，不会成为另一套武器库。
- `manaColors`、`manaCost`和`skill`是目录派生值，不是玩家或 AI 在战斗前临时填写的字段。

因此，最接近用户设想的接入方式已经存在：让 ST 只提供一个武器代码，前端执行 `anyWeaponById(code)`，就能得到技能描述、技能原型、法力色和耗蓝。

### 2.2 当前主角战斗快照的真实来源

`src/meta/systems/battleBridge.ts`的 `buildPlayerSnapshots()`目前走的是三消自己的 `MetaSave`：

- 主角身份从 `save.character`读取。
- 主角等级、职业和四维战斗面板来自三消的 `save.hero`、`heroStatsOf()`、职业和天赋系统。
- 当前装备武器由 `save.hero.equippedWeapon`解析。
- 武器对主角快照实际提供的是 `skillId`、`manaColors`、`manaCost`、技能显示信息和 `temperingLevel`。
- 虽然 `WeaponDef`目录行有 `attack/armor/health/magic`字段，但当前 `heroStatsOf()`的主角快照基底是三消职业/等级面板加淬炼，不会自动把这些目录字段当作 ST 六维或额外 DND 属性。
- `temperLevel`来自 `save.weaponTempering`，由 `forgeOps.ts`读取。
- 三消王国加成、同王国编队加成和三消天赋也会进入快照。

这意味着不能把 ST 的 `人物/装备列表`直接塞进 `buildPlayerSnapshots()`，也不能只把 `save.hero.equippedWeapon`改成 ST 名称。当前函数会继续读取三消职业、王国、天赋和队伍成员，最终仍然是 GoW/三消的编队逻辑。ST 模式必须新增一个独立的快照适配器，直接构造 `CombatantSnapshot`，绕开这套固定 MetaSave 编队逻辑。

### 2.3 三消部队和敌人的真实来源

当前三消部队不是 ST 羁绊角色：

- `src/data/troops.json`有 **1800 个**部队条目，约 **1795 个**不同的部队技能 ID。
- 部队通过 `troopId`进入 `MetaSave.collection`，拥有等级、升阶、特质槽和重复卡数量。
- `troopStatsAtLevel()`按三消部队成长数据计算生命、护甲、攻击和法强。
- `troopToSnapshot()`把部队转换成三消 `CombatantSnapshot`，技能使用部队自己的 `spell.id`，特质使用三消自己的 trait code。
- `encounter.ts`按三消王国池、稀有度和职责模板选择 `troopId`，`enemyDifficulty.ts`再计算敌人等级、特质数量和 NPC 面板。

所以 ST 模式不能复用 `planQuestEncounter()`、`planExploreEncounter()`或`enemyToSnapshot()`来生成任意世界观敌人。它们会要求三消王国和 `troopId`。ST 模式应该新增 `stEncounterCompiler`，把 AI 提供的敌人意图编译成通用的 `CombatantSnapshot`。

### 2.4 当前战斗协议可以复用

真正适合复用的是战斗协议，而不是 ST 的技能字段：

- `src/session/contract.ts`中的 `BattleRequest`/`BattleResult`。
- `CombatantSnapshot`中的 `externalId`、`templateId`、名称、四维面板、`manaColors`、`manaCost`、`skillId`、`traitIds`和`temperingLevel`。
- `src/session/hostProtocol.ts`和`PostMessageHostBridge`中的 `battle:ready`、`battle:start`、`battle:started`、`battle:result`、`battle:result-ack`。
- `validateBattleRequest()`对技能、特质、等级和面板范围的校验。
- `SkillPrototype`和注册表对三消棋盘效果的执行。

现有协议已经把永久养成和本场快照分开：宿主传入最终快照，战斗页只返回战斗结果。这正好适合作为 ST 与三消的边界。

### 2.5 当前三消淬炼和存档

三消武器淬炼已经有独立实现：

- `save.weaponTempering[weaponId]`保存每把武器的淬炼等级，缺省为 0。
- `forge.ts`按武器稀有度决定上限：Common/Uncommon `+5`、Rare `+6`、UltraRare `+7`、Epic `+8`、Legendary `+9`、Mythic/Doomed `+10`。
- `+1`到`+5`提供轮换的攻/甲/生/魔面板加成；`+6`起逐级解锁目录词缀。
- `forgeOps.ts`负责所有权校验、材料扣除、失败回滚和等级写回。

这个淬炼等级不应复制到 ST 的 `强化等级`后让两边各自修改。ST 只需要保存武器代码；如果希望玩家在酒馆侧看到淬炼进度，进度应由三消 IndexedDB 按代码保存，适配器只向 ST 注入只读显示。

当前本地三消存档实际使用 `localStorage`，不是 IndexedDB。`LocalSaveRepository`保存的是分片记录重新拼出的整份 JSON，`MetaGateway`文档也明确写着 local backend + localStorage。因此 IndexedDB 仍然是接入目标，需要另做 `IndexedDbSaveRepository`，不能把它当成现状。

## 3. 正确的武器代码方案

### 3.1 只保存代码，派生所有三消属性

推荐的最小持久化内容是：

```yaml
战斗桥接:
  武器代码:
    人物: gw_KnightsSword
    羁绊角色A: gw_ScoutsBow
```

或者把代码放在装备实例的专用字段中：

```yaml
装备列表:
  主手_01:
    名称: 叙事中的剑名
    类型: 武器
    武器代码: gw_KnightsSword
    # 其余字段仍是 AIRP 的文字装备字段
```

两种形式只能选一种，推荐单独的 `战斗桥接/武器代码`映射，因为它不会把三消目录字段混进 ST AIRP 装备 Schema，也不会让 AI 误以为三消技能属于 `资源技能`。

如果严格不希望修改 ST 变量结构，也可以把 `weapon-code:gw_KnightsSword`作为装备标签中的保留标签，但这只是兼容方案：标签容易被 AI 改名或重复写入，代码必须由辅助脚本归一化并校验。长期方案仍应使用专用映射。

### 3.2 代码由程序登记，AI 不负责随机数值

用户提出的“辅助计算脚本收到 AI 注册的装备后，程序化随机附加武器技能和法力颜色”方向可以采用，但要把随机发生点限制在**首次登记**：

1. AI 在 AIRP 中创建文字武器对象，提供名称、品质、描述和来源。
2. 辅助脚本判断它是新武器，按等级/品质/武器形制/剧情来源筛选一个合法的三消武器代码池。
3. 脚本一次性选择 `weaponCode`并写入桥接映射。
4. 以后每次读取都用同一个代码查目录；不再重新抽技能、颜色或品质。

不能在每次提示词刷新或每次打开 iframe 时 `Math.random()`重新附加，否则同一把叙事武器会不停换技能，战报、存档和玩家认知都会失真。随机选择必须使用稳定种子，或者首次选择后立即持久化代码。

### 3.3 通用世界观与现有 `gw_*` 代码的关系

`gw_*`代码是当前三消项目的固定目录代码，携带 GoW 目录中的名称、王国、角色定位和法力色。它可以直接作为第一版 ST 接入的**能力目录代码**，但不能把 `gw_*`的王国和职业语义强加给 ST 叙事。

长期建议把目录访问抽象为：

```ts
interface BridgeWeaponCatalog {
  resolve(code: string): BridgeWeapon;
  candidates(filter: WeaponCandidateFilter): readonly BridgeWeapon[];
}

interface BridgeWeapon {
  code: string;
  skillId: string;
  manaColors: readonly BaseColor[];
  manaCost: number;
  rarity: string;
  weaponTags: readonly string[];
  skillTags: readonly string[];
}
```

第一期 `BridgeWeaponCatalog`可以由现有 `weaponCatalog.ts`实现，代码仍然是 `gw_*`；后续增加 `st_*`或不带世界观语义的通用代码时，只替换 provider，不复制战斗引擎。

## 4. ST 模式的实际接入结构

### 4.1 三个数据层

**ST AIRP 层**：保存角色名称、六维、DND 等级、当前 HP、文字装备和剧情状态。它继续服务于 `单次激活`，不承担三消技能库。

**桥接层**：保存聊天分支存档、武器代码映射、角色颜色亲和、族群与蓝图引用、未完成战斗和结算收据。酒馆原生数值模式与战斗方式选择分别管理。

**三消数据层**：共享只读技能、图片与配方目录，按代码编译快照并执行棋盘和战斗；附加养成状态由酒馆宿主侧 IndexedDB 持有，iframe 不再保存另一份长期真值。

装备实例保存不透明能力代码；内部映射才引用 `gw_*` 等原目录代码，避免持久变量自动进入提示词时泄漏原身份。队友颜色与已装配能力另行持久化，不因主角换武器而重抽。最终数据契约见产品方案第 5、6、10 节。

### 4.2 ST 玩家快照如何组装

ST 模式应该增加类似 `buildSillyTavernSnapshots()`的适配器，流程是：

1. 读取 ST 当前角色和固定同行角色。
2. 读取主角装备实例的能力代码，以及同伴已装配的基础/魂片能力代码。
3. 从已适配目录取得技能、法力色、耗蓝与中立显示信息，并绑定族群、阵营等上下文。
4. 用 ST 当前 HP、DND 等级、六维、AC和一个明确版本的桥接系数，计算三消需要的 `hp/attack/armor/magic`。
5. 把 `skillId`、`manaColors`、`manaCost`、`spellName`、`spellDescription`和角色的稳定 `externalId`写入 `CombatantSnapshot`。
6. 从三消 registry 注册这些 `skillId`；未注册代码直接报错，不用 AI 文字兜底。

这个适配器**不能**调用当前 `buildPlayerSnapshots()`，因为那个函数会继续读取三消 `MetaSave.hero`、三消职业、王国加成、同王国编队加成、三消天赋和 troop collection。ST 模式应只复用最终的 `CombatantSnapshot`协议和引擎 registry。

### 4.3 ST 敌人快照如何组装

统一使用产品方案第 3 节的输入：对象/蓝图引用、等级、档位、职责、剧情权重、通用形态与可选特性/关系。叙事名字、具体种族名、具体职业名、外观正文不交给组装器；AI 不填写最终面板、原始技能 ID、内部图片配方 ID、伤害倍率或掉落数量。

程序解析族群关系、已适配技能和真实立绘候选，执行单体及全队预算，最后生成 `CombatantSnapshot`。持久蓝图关联能力、颜色与展示配置；重复遭遇不能重新抽一套能力。

通用敌人不转成原生 `troopId`，`templateId` 保持为空；`portraitUrl` 按通用形态和职责适配解析真实资源。技能和图片源 ID 留在内部，不带回原部队的名字、王国或固定种族身份。

## 5. 数值衔接：以 ST 为基础，不复用 ST 技能树

### 5.1 ST 可以提供的基础数值

`docs/辅助计算脚本.js`和`docs/酒馆变量`当前可提供：

- DND 等级和经验曲线：辅助脚本按 `floor(100 * level^1.5)`的累计曲线处理升级。
- 六维属性、当前 HP、最大 HP、临时 HP、AC。
- 武器文本的等级、品质、强化等级、属性加成和效果描述。
- DND 的每回合攻击次数：`Lv.1-19=1`、`Lv.20-49=2`、`Lv.50+=3`。
- DND 原生攻击、技能、豁免、动作和状态规则。

这些只用于构造桥接快照或继续跑 AIRP。ST 的 `技能树/资源技能`不能用来替代三消的 `skillId`。

### 5.2 三消快照需要的四维不是 ST 六维

三消引擎的 `CombatantSnapshot.stats`是 `hp/attack/armor/magic`，和 ST 的六维、AC不是同一量纲。当前三消 Meta 模式还会用自己的部队成长表和职业面板，不能直接拿来表示 ST 角色。

因此应建立单独的 `st-generic-v1`桥接公式，并把系数配置化：

```text
snapshot.hp     = round(ST 当前战斗生命基准 × hpScale)
snapshot.attack = round(ST 武器面板期望伤害 × attackScale)
snapshot.armor  = round(max(0, ST AC - 10) × armorScale)
snapshot.magic  = round(ST 施法属性/武器能力基准 × magicScale)
```

第一版不需要追求 DND 每次掷骰和三消每次消除的伤害完全相等，只需满足：

- 同一角色等级、武器代码和淬炼等级得到稳定快照；
- 同一 `battleId + seed + rulesetVersion`可以复现；
- 公式版本和系数写入战报；
- 原生 DND 战斗仍使用 ST 原规则，三消战斗只使用桥接快照。

### 5.3 武器淬炼应该挂在哪里

推荐：

- ST 只存武器代码；
- 三消 IndexedDB 存 `weaponCode -> temperingLevel`；
- 三消前端按代码显示淬炼等级、可解锁词缀和材料需求；
- 进入战斗时适配器把 `temperingLevel`作为本场快照可选字段传入；
- 战斗结果不会自行提高淬炼等级，升级必须走明确的淬炼命令。

如果确实要求酒馆 AI 知道淬炼状态，注入一段只读摘要，例如“武器代码、当前淬炼、已解锁词缀”，不要把完整词缀写进 `资源技能`。AI可以叙述武器变化，但不能改变三消库存。

## 6. 技能规模与 AI 使用方式

### 6.1 不把两千多技能全文塞进提示词

当前实际数据规模已经足够说明问题：718 把主角武器、1800 个部队、1795 个部队技能 ID，再加上技能库和特质库。把完整技能描述全部放入每次 ST 提示词既浪费上下文，也会让 AI 混淆 AIRP 技能和三消原型。

正确做法是三层数据：

1. **可执行层**：项目代码中的 `SkillPrototype`和效果原语，只接受注册的 `skillId`。
2. **索引层**：离线为每个 `skillId`生成机制标签、目标、形状、颜色、伤害类型、资源消耗、复杂度、稀有度和简短摘要。
3. **提示词层**：只给 AI 世界观中立的设计字段、威胁预算、组合约束与相关蓝图引用；具体 skillId 候选只由本地编译器消费。

现有 `src/data/weapon-skill-meta.json`主要记录技能保真度和缺失特性，它不是供 AI 检索的完整语义标签索引，需要另做 `skill-index`生成步骤。

### 6.2 技能候选流程

```text
AI 敌人意图
  -> 适配器按 manaColors/rank/form/role 确定有图组合
  -> 后续阶段再读取等级与所需技能机制
  -> skill-index 过滤
  -> 本地候选集（不注入运行时 AI）
  -> 预算校验与 SkillPrototype 编译
  -> BattleRequest.skillId
```

建议的标签组：

- 机制：伤害、治疗、护盾、增益、减益、控制、召唤、位移、资源、净化。
- 目标：自身、单体友方、全体友方、单体敌方、敌方全体、棋盘。
- 形状：单体、直线、邻近、随机、范围、连锁。
- 颜色/伤害：六色读写、护甲交互、真实生命伤害等实际引擎语义；不自动按颜色生成火、水、光、暗等叙事属性。
- 时序：施法前后、回合/消除触发、持续时间、使用限制等已实现行为；不把 AIRP 的附赠动作和反应直接当成三消动作。
- 适配：阶级、稀有度、等级范围、角色职能、复杂度和风险。

敌人预算可参考 `单次激活`中的威胁分档，但由编译器强制执行：每个对象先保持一个主动能力，高档位增加经验证的多段效果、被动和联动。多独立技能槽和复杂阶段属于后续扩展；AI 不能直接把 `3000%` 等数值写进技能。

### 6.3 同色队友技能

“把敌人技能装给同色队友”也不应使用 ST `羁绊列表/*/技能`直接覆盖。建议在三消 bridgeState中保存：

```json
{
  "memberId": "bond:guard",
  "colorAffinity": ["Brown"],
  "unlockedSoulSkills": ["skill.soul.source-01-control"],
  "equippedSoulSkills": ["skill.soul.source-01-control"]
}
```

装备校验由三消前端/核心完成：技能已解锁、角色颜色相交、槽位可用、等级和稀有度预算满足。ST 只接收一个可读摘要，或者由报告告诉 AI“某队友已学会某技能”。

## 7. 战斗触发和回传

### 7.1 AI 正文中的触发块

正则识别正文中的独立协议块，保留数据并显示 iframe 入口；不解析正文中的叙事设定。协议示例统一见产品方案第 3.3 节，不在调研里维护另一套字段名。

正则替换前，适配器必须：

- 读取 ST 当前变量和武器代码；
- 解析档位、职责、剧情权重、形态、蓝图与可选特性/关系；
- 校验代码、等级、威胁、关系、人数和可用图片；
- 根据固定种子编译已适配技能和面板，视觉使用独立种子；颜色等三消内部字段只留在 iframe 请求中；
- 生成 `BattleRequest`并通过现有 host bridge发给 iframe。

如果 AI 直接输出未知武器代码或无法满足预算的敌人，应返回可读错误，让 AI重新生成；不能静默采用另一个技能或把错误文本当作技能执行。

### 7.2 战斗完成后的报告

现有 `BattleResult` 不包含完整战斗过程，不能只转换终态就交付完整战报。需要扩展会话事件导出与缺失的因果信息，再由适配器生成中立的逐行动上下文；具体见产品方案第 9 节。下例仅示意结果与结算投影，不代表完整过程已实现：

```xml
<BattleReport battleId="..." result="victory" ruleset="st-generic-v1">
  <Outcome>胜利；完成 6 回合；e1 已失去战斗能力</Outcome>
  <CombatSummary>按回合压缩的消除、伤害、治疗和控制类别；不包含原始技能名或三消颜色</CombatSummary>
  <Survivors>人物 42/60；羁绊角色A 18/40</Survivors>
  <Settlement>
    <Currency name="灵魂" amount="30" />
    <Material name="普通钢锭" amount="2" />
    <SoulShard source="bridge-source-01" name="本场灵魂碎片" amount="1" progress="8/20" />
  </Settlement>
</BattleReport>
```

AI可以根据这份报告继续演绎，但不允许重算伤害、重新抽奖、增加掉落或改变魂片进度。若要更新 ST 当前 HP，只能由适配器生成白名单 `delta/replace`，并遵守 `docs/酒馆变量`中当前生命值和临时生命值的约束。

## 8. 存档和安全边界

### 8.1 IndexedDB 是目标，不是当前实现

用户希望游客模式、无云端服务器、浏览器级别本地存档，这个方向可行，但当前项目还没有做到 IndexedDB。建议保持现有 `SaveRepository`接口，新增：

- `profiles`：宿主/聊天/分支标识与桥接版本；
- `weaponBindings`：ST 角色/装备标识到武器代码；
- `weaponProgress`：武器代码到淬炼等级和解锁词缀；
- `soulShards`：`soulSourceKey`到进度和解锁技能；
- `battleTickets`：未完成战斗和 request 摘要；
- `settlementLedger`：`battleId + requestId`幂等结算；
- `outbox`：等待宿主确认的战报消息。

ST 附加模式建立独立存档，不自动搬入原生 MetaSave 的卡牌与王国进度；原生 localStorage 路径继续使用自己的存档。ST 存档提供导入/导出，并以宿主、聊天与分支划分命名空间。多标签页使用 IndexedDB 事务版本或 `BroadcastChannel` 处理冲突，不能用最后写入覆盖另一场已结算战斗。实际宿主 origin 与分支恢复规则见产品方案第 10 节。

### 8.2 iframe origin

ST页面和远端/localhost iframe不是同一个 origin时，不能直接共享 localStorage 或 IndexedDB。应通过 `postMessage`传输 battle request/result，且：

- origin必须显式白名单，禁止 `*`；
- `battleId`、`requestId`、版本和 payload大小必须校验；
- 同一 battle ID重复 start不能重开；
- 同一 result重复提交必须返回同一结算；
- iframe不直接写 ST变量，所有状态写入由 host adapter完成。

现有 `PostMessageHostBridge`已经有 origin校验、重复 start幂等和 result重投，可以直接复用。

### 8.3 结算明细

项目现有约束要求战斗结算页展示本场真实获得的物品、材料和货币。ST接入也必须遵守：

- `BattleResult`先进入结算账本，再渲染报告和结算页；
- 结算页显示真实名称和数量，不只更新 bridgeState或 ST 背包；
- 首胜、里程碑、活动挑战、随机掉落和魂片进度都逐行记账；
- 结算页不能重新抽奖；
- 重复 result不重复发奖；
- 三消 `gold/souls/gems`不要自动合并成 ST 的 `通用币`，除非 profile明确声明映射。

## 9. 单项目改造方向

在现有仓库内拆出通用战斗层与酒馆宿主适配层，具体目录职责统一见产品方案第 11 节。图片标注与技能索引工具生成共享数据；族群选择器、技能执行与战斗 UI 继续复用，不复制“ST 专用三消项目”。

三消现有 GoW 数据仍由 `meta`模式使用；ST通用模式不调用 GoW 王国池、三消职业、三消天赋和 troop collection，只共享：

- `BattleRequest`/`BattleResult`；
- `SkillPrototype`注册与执行；
- 战斗 UI 和 host bridge；
- 淬炼/材料/魂片等经过抽象后的结算账本；
- 技能索引和验证器。

现有模式继续使用自己的 `gw_*` 和 `troopId`，通用模式提交有语义的设计分类、蓝图引用与可选关系。两者共享机制实现，使用不同内容定义与状态；所有固定族群、王国与召唤依赖都需要显式适配。

## 10. 建议的实施顺序

分期和验收统一见 [产品方案第 12 节](sillytavern-battle-product-plan.md)。实施先后为：

1. P0：语义设计词表与映射规则、族群依赖盘点、全量技能适配索引，以及原始提示词解析、资源关联、文本打标和图片抽检工具与候选统计。
2. P1：独立敌人组装预览台，完成各稀有度至少 90% 适用敌人的组装验证，覆盖技能、同族联动、预算与实际卡片；晋升度、淘宝模式、魔头专用技能依赖单列排除依据。
3. P2：真实酒馆日常战斗闭环，含本地存档、恢复、HP 同步与完整逐行动报告。
4. P3：魂片、同色能力装配、武器淬炼和材料获取消耗。
5. P4：P1 各档达标后的剩余适用机制缺口、武器萃取与更多已确认资源；达到 90% 所需的普通召唤、变形和复杂机制在 P1 完成。

宿主通信与存储能力探针可独立做。P1 按现有敌人目录逐档出具完整组装覆盖报告，展示总数、特殊机制排除数、适用数、通过数与缺口；具体计算和验收口径见产品方案第 4.5 节。

## 11. 当前不应做的事情

- 不把 ST `技能树`、`资源技能`、`特质`接成三消技能库。
- 不把 ST 的文字装备 `效果`直接当作可执行 `SkillPrototype`。
- 不把三消 `gw_*`武器的王国、职业语义强写进 ST 世界观。
- 不让 AI 每次输出都重新随机武器技能和法力颜色。
- 不让 iframe直接写 ST变量或直接发放奖励。
- 不为 ST 再复制一套 718 武器、1800 部队和技能执行器。
- 不在结算页重新抽奖或让 AI 文本决定实际入账。

具体交付以产品方案为准：先让有真实立绘、抽象族群与可执行技能的敌人组装器可以独立预览，再沿同一边界接入酒馆和养成。
