# 宝石抽卡、愿望单与收集节奏模型

## 交付入口

- `game.html#wishlist`；宝石宝箱 → 愿望单。
- 图鉴详情：加入愿望单 / 管理愿望单。愿望单打开图鉴详情后返回保留检索、过滤和页码。
- 页面支持名称/编号/技能/特质多词交集搜索、王国、品质、颜色、种族、持有情况、只看已选、只看可加入、排序和分页。
- 桌面并排浏览和名单；手机有吸顶的筛选/已选跳转和补齐建议入口。
- 自动保存、实时配额、逐卡受限原因、按国清空、全名单清空确认、推荐预览确认、追寻目标/进度/暂停、概率说明。
- 推荐只补空位，按未拥有和当前队伍同色/同族偏好排序，使用最大流分配剩余品质与王国配额；不是强度推荐榜。已有特殊王国可能导致不足27人，预览显示实际结果，不替换玩家已有选择。

## 实际规则（单一配置源）

`src/meta/data/gachaRules.ts`：

| 参数 | 当前值 |
|---|---:|
| 王国数 | 最多9 |
| 每王国人数 | 最多3 |
| 总人数 | 最多27 |
| 每品质人数（传说/史诗/神话） | 各最多9 |
| 填满对应品质时名单内总概率 | 80% / 70% / 100% |
| 首次神话追寻上限 | 200抽 |
| 后续每轮神话追寻上限 | 400抽 |

这些是初始测试参数，不代表经济节奏已经通过玩家留存验证。版本号需随规则调整递增。

`src/meta/data/economy.ts`：单抽150宝石、十连1500宝石；基础品质权重 `[5200,2400,1700,500,180,20]`。

**十连只保底稀有或以上，不保底史诗。** 先掷自然品质；整批未达标时只把第十张低品质卡升至稀有。自然高品质结果保留。神话追寻发出的卡满足稀有或以上要求。

游戏品质索引：0普通、1精良、2稀有、3传说、4史诗、5神话。不要按英文稀有度名字推断中文档位。

### 概率口径

设当前品质的名单满额概率为 `a`，已选人数 `n`，该品质总人数 `N`：

- 每名已选角色的档内概率：`a / 9`。
- 名单内总概率：`n × a / 9`。
- 每名未选角色的档内概率：`(1 - n × a / 9) / (N - n)`。
- 未选择任何角色时，该档仍是全池等概率。

空位与名单外份额全部留在名单外，不会因为只选一人而把愿望概率全部集中到他。王国只约束名单容量，不参与额外抽签。品质基础概率不因愿望单变化；追寻替换是额外机制，须单独公示。

**指定一名愿望角色、关闭追寻时：**

| 品质 | 每抽自然命中概率 | 首次命中平均位置 | 持续十连的平均付费抽数 |
|---|---:|---:|---:|
| 传说 | 5% × 80% / 9 ≈ 0.4444% | 225 | 229.54 |
| 史诗 | 1.8% × 70% / 9 = 0.14% | 714.29 | 718.80 |
| 神话 | 0.2% / 9 ≈ 0.02222% | 4500 | 4504.50 |

因此新模型中史诗确实比传说更难获得。名单内角色使用固定槽位概率，不再拿整个品质池人数当分母。

满额名单中“任意一名愿望角色”的平均自然间隔约为 `1 / (0.05×0.8 + 0.018×0.7 + 0.002) = 18.32` 抽；这不等于某一名角色的首获，也不等于集齐27人的时间。

### 神话首张追寻

- 指定愿望单中一名**真实未拥有**的神话。收藏修改器启用时用 `collectionTruth` 判断真实持有。
- 仅宝石抽卡、且存在有效目标时累计。金钥匙和荣耀不推进。
- 上限触发时**替换这一抽**为目标，不额外发卡。十连仍只发10张。
- 自然命中目标也结束本轮。其他神话不重置。
- 更换、移除、暂停目标保留已有进度；移出名单自动暂停。
- 目标通过别的途径获得后，下次宝石抽卡会暂停目标、保留进度，页面也显示暂停。
- 完成后清空目标、进度归零、完成次数增加；下一轮使用后续上限。十连余下卡不自动开启新目标。
- 开始累计的轮次保存 `limit` 快照，日后调参不追溯增加其上限。
- 示例：进度199时单抽最多花150获得目标；选择十连则整组支付1500，不退还余下9抽。

## 宝石预算模型

运行：

```sh
npm run economy:gacha -- light
npm run economy:gacha -- standard
npm run economy:gacha -- active
npm run economy:gacha -- weeklyLight
npm run economy:gacha -- weeklyStandard
npm run economy:gacha -- weeklyFull
npm run economy:gacha -- docs/events-budget.example.json
npm run economy:gacha -- docs/gacha-budget.example.json
```

`src/meta/economy/gachaModel.ts` 是纯模型；CLI通过Vite加载TS，与游戏共用奖励、价格、权重和愿望参数。

### 预算口径

```text
每周净宝石 = 首胜 + 竞技场奖励 + 活动里程碑/守土/共享周目标 + 入侵周结算 + 寻宝
           + 其它经常性收入 - 竞技场报名费 - 其它消费
每日抽卡预算 = max(0, 每周净宝石) × 抽卡分配比例 / 7
```

- 首胜天数0~7，读取实际首胜奖励；竞技场按最终0/1/2/3胜分布加权，首场每周免费，其余扣报名费。
- 活动各自里程碑按输入周积分读取 `EVENT_MILESTONES`，同一周只算一次；守土奖励使用 `EVENT_DEFENSE_REWARD` 并受现有周上限约束。
- 入侵周结算分布顺序为晋级/保级/降级/未参与；读取 `INVASION_SEASON_REWARDS`。
- 寻宝输入每周局数及八档终盘物件平均数量（总和64），读取真实奖池每个物件的宝石期望。该输入依赖玩家终盘数据，不假设每局满金库。局数还需满足藏宝图供给。
- 战斗内收集等来源归入 `otherWeeklyIncome`，由设计师填入实测/明确假设；非宝石材料没有偷偷折算为宝石。
- `otherWeeklySpending` 包含购买/其它系统宝石支出，竞技场报名已经独立扣除，避免重复扣。
- `startingGems` 是一次性可用于抽卡的库存，只抵扣累计所需宝石，不计入每日产出。不要把新手礼包/演示钱包当作持续收入。
- 可选来源不填就是0；所有预设是**假设情景，不是玩家统计**，也不是全部玩法自动满勤收益。
- 输出包含收入分解、净抽数预算、无愿望单/有愿望单对照、首次命中期望、整十连付费期望、P50/P90、首次/后续追寻上限、库存折算、风险提示和30/60/90天校准建议。
- 时间是固定平均预算的**等价天数**，不等于随机收入、每日离散结算、中途消费情况下真实首次获得天数的数学期望。持续净预算为0且库存与可获得的首通收入仍不足时输出 `Infinity`；库存足够则预算天数为0。

### 精确抽卡模型与边界

对一个十连内部保留“此前未命中目标且是否已达稀有保底”的两态概率，逐张传播；用整批未命中概率连接后续批次。这样不会把有批次依赖的保底当独立伯努利抽签，也不会把首命中位置直接当整十连付费抽数。

指定目标的追寻采用截断生存分布；`pursuitRemaining` 支持当轮剩余抽数。目标不变且未拥有是预测前提。传奇/史诗预测未叠加另一个神话目标正在追寻时的替换影响；整个收藏进度与毕业时间也不是单一目标倒数。模型没有按玩家个人收入暗改概率。

### 当前参数的风险与调参工作流

`light` / `standard` / `active` 保留为不参与活动的对照组；重做后的参与情景使用 `weeklyLight` / `weeklyStandard` / `weeklyFull`。

`standard` 对照假设：每周首胜7天、竞技场3局，0/1/2/3胜占10/20/40/30%，无其它收支，全额用于抽卡，初始库存0。

- 每周350首胜 + 504竞技场奖励 − 300报名费 = **554净宝石**。
- 约79.14宝石/日，仅3.69抽/周。
- 首次200抽追寻，平均约195.84付费抽 / 29,376宝石，折合约371天；上限约379天。
- 后续400抽追寻，平均约383.16付费抽 / 57,474宝石，折合约726天。

**在该有限收入情景下，200/400明显不是适合快速建立阵容的节奏；但也不可把它当成全玩法收入结论。** 完整收入要把实际活动、入侵、寻宝等填进去再算。模型对首次上限超过90天的情景输出风险提示。

调参流程：

1. 输入目标活跃度、各玩法完成度、胜率分布、其它消费、抽卡分配比例与实测来源。
2. 明确“首次目标”和“后续每名目标”的期望周期；建议同时看平均与P90，避免只看均值忽略尾部体验。
3. 校准建议 `targetDays × dailyGachaBudget / singlePrice`，按10抽取整；零预算不给出虚假建议。
4. 若保留200/400，首次60天上限需要每日约500净抽卡宝石；后续120天上限同样需要约500/日。这里的500是**目标预算反推值，不是当前实际收益**。
5. 修改 `economy.ts` / 各玩法单源奖励，或 `gachaRules.ts` 追寻上限，递增规则版本；重跑模型和测试。
6. 存档已开始的追寻轮次保留原快照，下一轮使用新值。价格和概率作为统一规则调整，不做隐式分人群变动。

## 存档、审计与测试

- 新档初始化，旧档缺字段默认空名单；损坏名单去重、剔除无效角色/超额项，追寻进度有限值校验。
- 网关独立提供 `setWishlist` / `setPursuitTarget`，页面全部经网关写入。
- 宝石抽卡日志保存规则版本、名单、追寻前后状态及逐卡来源（自然/稀有保底/追寻）。重载保留审计记录。
- 确定性要求相同种子、规则和初始存档（含收藏、名单、进度）；仅种子不足以复算不同配置的结果。
- 单元覆盖：配额、补齐、旧档、持久化、自然命中、阈值替换、十连交互、切换暂停、真实持有、失败原子性、其它宝箱隔离、收入预算、精确分布与种子模拟。
- 浏览器覆盖：桌面/手机检索、加入、追寻、详情返回、重载、预览确认、清空、宝箱入口和第200抽实际入账；图鉴与宝箱原有视觉回归同步检查。


## 王国逐关首通宝石（2026-09-25）

### 奖励与总量

金额单源：`KINGDOM_FIRST_CLEAR_GEMS`（`src/meta/data/economy.ts`）。
关数单源：`KINGDOM_STAGE_COUNTS`；全图数量从 `KINGDOM_ORDER` 派生。

| 难度 | 每关首通 | 每王国关数 | 每王国小计 | 当前42国总计 |
| --- | ---: | ---: | ---: | ---: |
| 普通 | 100 | 8 | 800 | 33,600 |
| 困难 | 200 | 3 | 600 | 25,200 |
| 非常困难 | 300 | 3 | 900 | 37,800 |
| 合计 | — | 14 | 2,300 | 96,600 |

- 当前全图588关，150宝石/抽，首通全部投入抽卡约644抽（64次十连+4次单抽）。每王国约15.33抽，2个王国普通全通1,600宝石约10.67抽。
- 设计目的：普通线提供早期积累，更高难度给更大的单关奖励；属于有限推图福利，不是无限刷取收入。
- 首次200抽追寻加后续400抽追寻，若两轮都到上限共需600抽。全图首通全额用于抽卡时可支付这两轮、剩余44抽，但需完成588关；这不等于配齐愿望单或培养毕业。自然提前出卡仍按原概率发生。
- 普通线8关，每关成功推进各领一次；困难/非常困难分别按真实获胜关号记录，高难度可跳打，打第3关不会代领1、2关。
- 重复挑战、失败不发首通奖励；跨日、重新进入、读档不重置首通标记。每日首胜50宝石和战斗内收集仍独立结算、可叠加；活动/竞技场/入侵不领取这笔王国首通奖励。
- 页面固定显示“首通 +金额 宝石”，完成后显示“首通已完成”；高难度已完成关仍可挑战材料。

### 有限预算而非永久周薪

可选输入 `kingdomProgress`：

```json
{
  "kingdomProgress": {
    "remaining": { "normal": 336, "hard": 126, "veryHard": 126 },
    "weeklyClears": { "normal": 16, "hard": 3, "veryHard": 1 }
  }
}
```

- `remaining` 是尚未领取奖励的关数，非负整数，上限为该难度全图关数。已有存档可用 `remainingKingdomFirstClears(save)` 从真实进度导出；未解锁的后续王国仍属于未来剩余内容。
- `weeklyClears` 是预计每周**新增首通**速度，不是重复胜场；各难度独立耗尽。速度需符合玩家实际战力与解锁节奏，模型不把未解锁奖励瞬间发到钱包。
- `kingdom.remainingGems` 给出剩余奖励池，`firstWeekGems` 是首周预计推图收入；`firstWeekGachaGems` 是扣除支出后、按分配比例可用于抽卡的首周新增预算，不含初始库存。
- 原有 `netWeekly / dailyGacha / weeklyPulls` 保持**持续收入**口径，`calibratePursuit` 也只使用持续收入。首通不可再放进 `otherWeeklyIncome`，否则会重复计算。
- 预测逐段求解 `库存 + max(0, 持续净收入×天数 + 各难度 min(剩余关数, 周速度×天数/7)×奖励)×抽卡分配比例`，达到指定宝石预算的最早日期。每个难度耗尽后都停止产出。
- 这是平滑推图假设的预算等价日期，不是逐日离散领奖、战力卡关和抽卡结果相互影响下的实测周期。首次/后续追寻报表是使用相同输入的独立对照；规划连续两轮时，需要更新剩余关数与库存，首通资金只花一次。

当前 `docs/gacha-budget.example.json`：按新版活动表每周持续净收入1,858.8宝石，推图首周另得2,500，80%用于抽卡，首周抽卡预算3,487.04宝石，约23.25抽。含初始150宝石，首次追寻平均付费预算约58.67天、上限约59.92天。该例使用显式活动积分，未输入共享胜场，故不计共享周目标收入；完整周常参与示例见 `docs/events-budget.example.json`。这是输入假设下的预算换算，不是实测获取承诺。

### 旧档兼容

- 普通沿用 `questsDone` 判定历史完成；本次更新不自动补发已经完成的普通关奖励，也不重置任务进度。
- 旧档只保存高难度的**选中档位** `exploreTier`，未保存逐关获胜历史。因此不据此推断通关；新增 `clearedExploreTiers` 缺失时按空表处理，更新后每个高难度关第一次获胜可领取一次。
- 新标记与钱包在同一次网关结算持久化，水合时过滤非法档位、去重；无需清档。普通历史补发如需运营补偿，应独立定义一次性补偿批次，而非反复读档发钱。


## 周活动参与模型（2026-09-25）

活动规则、页面结构与奖励预算详见 `docs/events-weekly-rework.md`。

- `eventParticipation` 为各活动输入胜场、败场、路线、每局分钟、配队加成与连胜长度；模型从运行时奖励表计算宝石，不额外维护一张收益表。
- `route: "risk"` 对应突围/强攻/护送/职业考验；省略为普通路线。职业考验假定主角存活。
- 世界物资采用每胜7或11加匹配角色数的均值估算；阈值附近可能受随机掉落影响，不等于精确越线概率。
- 同一活动的 `eventPoints` 与 `eventParticipation` 二选一，重复输入会报错。显式积分不反推胜场；使用 `eventWeeklyWins` 单独给出共享胜场，或由参与场次自动合计。
- `budget.events` 已含共享奖励与守土宝石，`eventShared` 仅为其中分项，避免再次相加。
- `eventMinutes` 只覆盖显式参与场次，败场计时间、不计胜场奖励；不含编队、加载、商店或其他日常。

| 假设情景 | 活动宝石/周 | 含首胜竞技场的净宝石/周 | 抽数/周 | 活动估算分钟/周 |
|---|---:|---:|---:|---:|
| weeklyLight | 1,640 | 1,854 | 12.36 | 42 |
| weeklyStandard | 3,960 | 4,514 | 30.09 | 108 |
| weeklyFull | 5,480 | 6,034 | 40.23 | 243 |

以上按100%净预算用于抽卡、无库存/首通/其他收支。标准情景首次指定神话追寻平均约45.55天预算、200抽上限约46.52天；后续追寻平均约89.13天预算。该版本只提高可规划的活动收入，保持抽卡价格、品质概率、愿望份额和200/400追寻上限；十连仍只保底稀有或以上。先观察实际参与、战斗时长与资源消费，再统一调整公共参数。
