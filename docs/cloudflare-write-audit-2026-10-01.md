# Cloudflare 写入审计与优化（2026-10-01）

## 结论与范围

此前邮件涉及的主要写入来源是每玩家 `PlayerActor` 的 **Durable Objects SQLite**，不是项目 D1 表本身。
请求量确实增长，但旧代码存在可复现的重复写入，尤其是防守页/地图的无变化同步。
注册账号、活跃对象和 RPC 请求数不是同一个口径，应区分写入次数与真实用户数。

本次仅修改本地代码、执行本地测试和构建，未部署 Worker，未修改线上数据。
工作区已有的区域 PvP、养成与 UI 改动保持原样。

## 原有重复写入路径

### 防守同步

即使没有新战报，原流程仍执行：

1. 更新时间戳 `defenseLog.fetchedAt`，无条件设置待发布标记。
2. 落盘 `meta`、`invasion` 两条记录。
3. 向 D1 发布相同镜像、上报相同周榜 VP。
4. 清除待发布标记，再落盘 `meta`、`invasion` 两条记录。

一次空同步共 **4 条 DO 记录 UPSERT**，另有 D1 镜像/周榜写入。
前一阶段本地 workerd 计量验证：已有记录的同值 UPSERT 也会计入写入；带主键索引的新行插入可能计入额外索引写入。
因此减少 SQL 调用并不总等同于减少同样数量的计费行，本次优先消除整个无效写入路径。

### 其他路径

- 所有成功命令都增加 `revision` / `savedAt`，即使真实状态没有变化。
- 背包每次挂载都发送 `markMaterialsSeen`，已读状态仍造成一次 meta 更新。
- 玩家对象每次冷启动重新收到身份参数时，都重复持久化同一身份。
- 周榜同值 UPSERT 仍更新 `updated_at`，同时可能改动排名相关索引。

## 本次实现

### 1. 防守发布按变化去重，保留保鲜与重试

文件：`src/meta/systems/invasionDefense.ts`、`src/meta/server/core.ts`、`src/meta/server/host.ts`、`src/meta/state/schema.ts`、`src/meta/state/save.ts`。

- 新增 `invasion.lastDefensePublish`：只保存已确认发布成功的镜像指纹和时刻。
- 指纹覆盖阵容、属性、VP、联赛、周次、规则版本等已发布字段，排除观察时间 `recordedAt`。
- 内容变化、首次发布、时钟回退或距上次成功发布满 30 分钟时，才设置待发布标记。
- 30 分钟保鲜由后续相关操作触发，不为所有离线玩家创建周期定时器。
- 指纹确认与清除待发布标记放在原有同一 ACK 批次，不增加额外批次。
- 已待发送的发布不会被去重取消；D1 失败或本地 ACK 落盘失败后仍可重试。
- 防守日志先统一字段顺序与可选字段，再比较内容；只有 fetchedAt 不同不再改存档。
- 新战报的游标、奖励、VP、复仇状态照常处理。已有旧存档把缺失字段补为 null，无 SQL 迁移。

### 2. 无状态变化命令不落盘

文件：`src/meta/server/core.ts`、`src/meta/server/host.ts`、`src/meta/server/protocol.ts`、`src/meta/gateway/commandGateway.ts`、`src/meta/screens/bagScreen.ts`。

- 比较命令前后真实存档内容，排除顶层 bookkeeping 字段 `savedAt`、`revision`。
- 成功但无变化时返回 `commit:false`、`patch:null`，不增加版本。
- 无变化命令仍可重试上次失败的脏记录落盘，仍执行需要重试的外部副作用。
- 回执附带权威 `revision`；客户端即使收到 null patch，发现落后也走保留战斗票据的只读同步。
- 无脏记录时不调度空的延迟 flush。
- 背包仅在材料确实未读时发送已读命令；服务端仍独立处理旧客户端重复请求。

### 3. 周榜相同值不重写

文件：`src/meta/server/host.ts`、`worker/src/mirrorPool.ts`。

- 同一活跃 Actor 内，仅缓存成功上报的 weekStart / league / VP 组合。
- 上报尝试前清除旧成功缓存，防止丢 ACK 后 A → B → A 被错误跳过。
- D1 UPSERT 增加条件：owner_key、league、vp 均未变化时不更新行。
- Actor 重启后的首次核对仍可能发出 SQL，但相同数据没有实际行更新，且保留原排名时间戳。
- 写接口缺少玩家身份时抛错，避免将未执行的写入当成成功确认。

### 4. 身份只在首次缺失时写入

文件：`worker/src/playerIdentity.ts`、`worker/src/playerActor.ts`。

- 冷启动读取既有身份，身份相同不再 put。
- 同时到达的 alarm/load/execute 绑定串行化，初次创建只写一次。
- 身份写成功后才暴露给共享池；读写失败可重试，身份不匹配不覆盖已有值。

## 本地复现结果

统计对象为真实 MetaHost 提交给存储层的记录批次；共享池使用测试替身，非线上计费采样。

| 场景 | 优化前 | 优化后 |
|---|---|---|
| 已初始化、未到保鲜时间、内容不变的防守同步 | 4 条 DO 记录更新，重复发布镜像和 VP | 0 条 DO 记录更新，仅保留战报读取 |
| 材料已经读过，再执行已读命令 | 1 条 meta 更新 | 0 条记录更新 |
| 相同防守阵容重复部署 | 再次发布并落盘 | 保鲜期内无变化不再写入 |
| 已有身份的 Actor 冷启动 | 重复 put | 读取一次，0 次 put |
| 冷启动后的相同周榜上报 | UPSERT 更新行 | 条件 UPSERT，SQLite total_changes 不增加 |

首次初始化、旧存档字段补齐、真实战报/奖励变化，以及 30 分钟保鲜到期仍有必要写入。
**这不是全站写入下降 100% 的承诺。** 总体节省比例取决于空同步在真实流量中的占比，上线后应按相同 UTC 时段及请求量比较。
