# 酒馆运行时 AI 遭遇协议

本协议让 assistant 提交待战遭遇的语义需求，由程序校验并组装敌方。`runtimeProtocol.ts` 提供协议解析与运行时提示词；宿主与面板提供消息启动桥，消息读取、入口卡片以及真实结算到 AI 的自动回注由各模块接线和验收。这份文档不代表整版酒馆链路已完成。

## 实际使用

可直接使用 [运行时提示词文件](sillytavern-runtime-ai-prompt.md) 和 [ST 正则 JSON](sillytavern-runtime-regex.json)，也可在公开安装页重新下载当前版本。提示词是 EJS 模板，应原样加入现有世界书，由角色卡现有的提示词模板扩展在发送前执行；下载文件本身不会自动安装条目。EJS 沿用《战斗规则》的 `getMessageVar('stat_data', { defaults: {} })` 读取消息变量：三消模式为布尔 `true` 且未屏蔽战斗上下文时，才注入三消规则；模式关闭或缺失时三消模板输出空文本。AI 只接收渲染后的规则，无需读取开关或选择战斗模式。

配套 [原生战斗规则](战斗规则.md) 已增加互斥条件：三消关闭且未屏蔽战斗上下文时才注入原生规则。启用“屏蔽战斗上下文”时，两份模板均输出空文本。使用两份规则的角色世界书需要同步更新两个条目；本地文件和公开下载的更新不会自动替换角色卡已安装的世界书。

消息入口从选定的原始 assistant 消息获取完整 `text`，调用 `parseRuntimeEncounter(text)`。不要先截取首个匹配块、清除尾部或使用渲染后的 HTML 解析，否则会掩盖多块和格式错误。AI 只提交 `{enemyDesigns:[...]}`；解析器补齐内部版本、基础配置标签和倍率，并将缺省效果规范化为空意图，返回 `{version:1,difficulty:string,enemyDesigns:EnemyDesignInput[]}`。这是语义计划，解析成功不代表已选到真实立绘或完成组装。

导出的 `MATCH3_BLOCK_PATTERN` 是无斜杠分隔符、无 flags 的正则 source，可以传给 `new RegExp(MATCH3_BLOCK_PATTERN)`，第一个捕获组是 JSON 文本。它只提供格式定位，不能替代完整消息校验。提供给酒馆的正则配置 JSON 和消息入口由独立模块负责。

宿主在来源、模式和聊天仍有效时，把语义计划交给既有编译与准备流程；种子、请求标识、规则与预算由程序管理。提示词只安排剧情触发判断、敌人基础配置、输出入口并等待、接收战报续写四项任务。每名敌人只填 `name`、`race`、`rank`、`level`、`form`、`role`、`manaColors`，`effects` 由组装器自动生成。AI 不填写效果清单、随机权重、机制数量或内部字段，也不挑技能、特质或资源 ID。战后 AI 的任务是接收程序提供的本场战报并续写剧情。战果记录的选择、内部编号核对、去重与投递归程序处理，不要求 AI 读取变量镜像或核对内部记录；实际投递链路的完成情况见下文。

## 提示词精简审查

审查纳入战前提示词独立盲审意见，以 AI 的四项任务为边界；格式要求与叙事所需的对应关系继续保留，程序限制留在解析器及其测试中。

## 消息启动与幂等

消息入口通过 `MessageEncounterSource` 传递完整原文与聊天、角色、消息、身份和 swipe 信息。调用宿主 `playMessageStory(source)`，或面板的同名方法；原有 `playStory` 和 `playReplay` API 继续可用。面板先取得当前聊天存档，缺失时创建；三槽已满时打开管理界面，由用户决定删除哪个旧存档。准备或战场打开期间的并发启动报错。

`battleId` 为存档 ID、chatId、characterId、messageId、messageIdentity 和 swipeId 按元组稳定序列化后的 SHA-256，不包含遭遇内容。`requestId` 为 `[上述消息身份元组, 解析后的完整计划（含 version）]` 的稳定 JSON 的 SHA-256；种子取 battleId 前八个十六进制字符对应的整数。这样同一消息身份的内容变化仍绑定原 battleId，并由 requestId 检出冲突。

同 battleId 的待战 ticket 及 requestId 一致时恢复原快照，不再准备或重编敌人。同 battleId 已有结算且 requestId 一致时打开存档面板显示原收据，不重开战、不重奖；计划变化则报错。其他待完成战斗会阻止新战；有待保存 outbox 时先提示保存结果。新开和恢复待战均检查来源仍为最新消息，并在队伍确认后重查来源、模式和聊天；历史消息可查看已有原结算。管理面板恢复剧情 pending 时也先核对冻结 origin 的消息、swipe、存档绑定和变量指纹；来源变化会在开战前拦截，保留备份与手动放弃入口，避免已知无法同步的旧战斗进入结算队列。

## 冻结格式与示例

一条 assistant 消息最多一个块。标记大小写固定，分别独占一行，不缩进、不附带空格、不加 Markdown 代码围栏；标记间是合法 JSON。支持 LF 和 CRLF。

```text
守卫在门前列阵，等待你迎战。
<match3>
{"enemyDesigns":[{"name":"遗迹守卫","race":"人类","manaColors":["Red"],"rank":"杂兵","form":"人形","role":"Striker","level":20}]}
</match3>
```

上面代码围栏仅用于文档排版，实际消息从叙事正文开始，直接输出两个标记。输出结束标记后立即停止，不续写战斗结果。

当前 AI 输出顶层只填写 `enemyDesigns`，为 1 至 4 名敌人的数组。每名敌人只填写 `name`、`race`、`manaColors`、`rank`、`form`、`role`、`level`。颜色为六色非空无重复集合，等级为 1..100 整数。AI 依据遭遇选择主职责，技能效果及机制组合由组装器自动按权重生成，无需设计主副效果或指定机制数量。

解析器统一补入内部版本 `1`、配置标签“基础”、敌人数值倍率 `1` 和 `assembly:"classified"`，交给共享编译器。缺省 `effects` 规范化为 `[]`，表示没有额外效果意图，不补入 `damage` 或其他默认机制。`version`、`assembly` 和 `storyWeight` 由程序处理，不出现在 AI 提示词或新消息示例中。

三消难度与血量倍率属于三消自己的独立设置，不读取 AIRP 的难度或分档 HP/伤害倍率。普通／困难与两档动态难度仅记录为后续方向，血量倍率设置也留待后续接线；当前基础链路不实现难度系统，不让 AI 选择额外倍率。

新剧情遭遇的个体生命、攻击、护甲和魔力由程序在标准面板上分别随机上浮或下浮 5%～10%；四项独立取值，四舍五入为整数，零值保持零，生命至少为 1，并遵守原有面板上限。程序按遭遇种子与队伍位置产生独立浮动种子，实际数值进入开战快照；刷新、恢复及往昔再现沿用原配置。AI 不填写浮动参数。这是本场个体差异，与后续普通／困难、动态难度及独立血量倍率设置分别处理。历史配置未记录浮动种子时保留原数值。

兼容已有消息显式提供 `version:1`、顶层字符串 `difficulty`、成员数值 `difficulty`、`storyWeight`、`assembly:"classified"` 和旧 `effects` 输入。旧效果字符串数组仍转换为必需效果约束；旧对象项的 `required`/`preferred` 保留原语义。显式旧效果仍须来自共享词表且不重复，多项必需效果须在同一名敌人的完整主动及所选特质中全部满足，缺少必需效果时返回组装诊断。这些值仍按共享校验验证并保留，使旧消息解析后的计划及请求标识不变，已有 pending/receipt 可继续恢复。固定组装方式的冲突值仍报错。共享手动设计器与历史存档格式保持原有语义；这些兼容字段无需 AI 在新消息中填写。

顶层或嵌套输入的 `seed`、`rules`、`budgetPolicy`、`enemies`、任何内部 ID 与未知字段都报错。内部标识包括但不限于 troop、portrait、recipe、ability、trait 及 external ID。合法枚举和值域由 `ENEMY_DESIGN_VOCABULARY` 生成提示词，避免维护第二套词表。

以下为程序解析器限制，不写入面向 AI 的提示词：协议块上限为 **32 KiB，即 32768 个 UTF-8 字节**，计算从 `<match3>` 开始到 `</match3>` 结束的标记、JSON 及内部换行。中文和 emoji 按实际 UTF-8 字节计数；块外的长篇叙事和分隔换行不计入上限。仍须从完整原始消息校验块数量与标记结构，不应先截短正文。

缺块、多块、标记不配对、非独立行、嵌套、代码围栏包装、超长、坏 JSON、顶层结构错误和未知字段都有具体中文错误。敌人校验保留共享诊断并增加 `enemyDesigns[index]` 定位。仅因合法的 JSON 结构通过校验，不代表语义组合一定有可用配方；实际编译仍可能返回无立绘或效果约束不满足等诊断。

## 选图、机械配置与历史记录

新 classified 立绘优先按 rank/form/role 选取，缺同职责图片时从同 rank/form 选择其他视觉职责图片；图片职责不改变机械职责。manaColors 不参与选图。档位和形态仍匹配真实资源，没有视觉候选时保留 no_exact_match 诊断。有图不代表机械组装可用，完整主动、特质及机制约束仍由组装器校验。

等级参考当前区域和任务难度，不与玩家等级绑定；3 个及以上同类型敌人须混合不同兵种，保留集群战术要求。档位配色保留：杂兵单色，精锐／首领／领主双色，传奇三色。战法仍由 AI 只选主职责，具体技能、特质与效果组合由程序生成。generation v2 的实例充能配色独立绑定并规范排序；源主职责、原始稀有度、充能费用、效果公式及技能内部固定颜色继续来自原生模板。供魔档案按绑定后的实际配色计算。generation v1 和无 generation 旧档保留原选择器，恢复时不迁移。

旧画像保存的 query 中若含颜色，该颜色仅用于历史记录与原绑定的一致性验证，不参与新选图或换图筛选。已有蓝图和待战快照复用已保存的真实图片及机械配置，消息身份、请求标识与重复结算规则沿用原协议。实现、可下载提示词及本地预览已同步；冻结的旧生成存档和旧版无 generation 存档均通过恢复验证。跨颜色换图、保存与重载已有浏览器回归。样本与边界见仓库内 `docs/sillytavern-portrait-mana-decoupling.md`。

## 语义职责与结算边界

程序按 rank/form 优先匹配同职责的真实立绘，manaColors 单独用于实例充能；组装器负责完整主动及独立特质的选择、权重和机制组合，并验证实际职责、源稀有度、费用与固定效果契约。颜色仅表示法力，不代表火、水等世界观元素。主职责与附带能力分离，供魔角色附带伤害仍属供魔；具体组装规则见 [设计准则](sillytavern-enemy-design-guidelines.md)。

新消息省略效果后，解析器提供空意图，具体效果由程序按主职责与内置权重生成。条件、概率、目标和分支由真实配方保留，拥有某机制不等于每次必然触发；分支独有效果不当作确定能力。职责权重、复杂度、强力机制准入、伤害形态、宝石参数及召唤规则均属于程序组装策略，AI 无需计算或填写。

AI 输出块后停在待战，真实战报之前不预演回合、不宣布胜败、不扣 HP、不发奖励。真实结算后，玩家在结算页点“继续”，程序把战报作为一条聊天消息发给 AI，见下文。

AI 根据收到的战报续写。程序负责发奖、结算展示与报告内容的一致性：该场真实入账的材料、物品和货币，包括首胜、活动进度、里程碑和周活动奖励，必须在本场结算页显示真实名称及实际数量；胜败、未发奖与重复提交应和真实入账一致。结算页不重新抽奖，不用预览奖励代替实际收据。具体口径见 `battle-settlement-rewards.md`。

## 战后输入的现状与协议边界

现有剧情同步只把生命写回 MVU，并在聊天变量 `match3.storyResults[battleId]` 记一条简短确认（`version`、`battleId`、`requestId`、`resultDigest`、原消息与 swipe）。完整的 `result` 和聚合 `report` 只在本地存档的结算收据里；AI 通过【三消战报】消息得到战斗事实。

`report` 包含胜方、回合数、击败敌人 ID、我方倒下/复起 ID，以及每名角色的初末生命、生命百分比、净生命损失百分点、累计受伤/治疗、倒下/复活次数和最终倒地/逃离事实。AI 只能叙述这些已证实事实。相同颜色或相同能力需求不代表具体施放过某个招式；没有完整行动记录时，不补造回合过程。

正式结算收据在存档的 `settlements` 中保留 `grants`（实际魂片/奖励）和已学能力等信息。MVU/聊天战果镜像仍不含完整奖励列表和行动事件。

2026-10-28 起，战报通过聊天消息送达 AI：剧情结算页点“继续”时，`formatStoryReportMessage`（`src/sillytavern/storyReportMessage.ts`）从本场收据生成以“【三消战报】”开头的中文文本，包含战斗结果与回合数、每名敌人被击败／逃离／剩余生命、我方每人初末生命与倒下复起、本场实际获得（魂片按“敌人名的灵魂碎片”命名）及新学会能力，不含内部 ID。`sendTavernChatMessage` 参照底栏经营页“出发”的做法，写入酒馆 `#send_textarea`、触发 `input` 后点击 `#send_but`。每场只发一次；发送失败时结算页提示，再次点击关闭。放弃战斗按败北生成同样格式的战报。提示词 2.4 节要求 AI 只根据该消息叙述战斗事实。本机真实酒馆已验证 AI 收到并按战报续写。战报是聚合结果，不包含逐行动过程，AI 不应补造具体招式。

正则导入配置由 `createRuntimeRegex(baseUrl)` 生成，安装页下载实际 JSON；匹配 AI 输出中的 `<match3>…</match3>`。替换模板采用含 `<body>` 的 fenced HTML，以满足真实酒馆助手的前端识别。它不引用 JSON 捕获组，模块使用 `getCurrentMessageId()` 读取原消息。

## 候选版数据兼容范围

## 第二轮独立盲审与修订

盲审者只读取冻结提示词，先保存六份战斗回复和三个流程探针，再写审查；没有读取实现、成功组合或历史结果。第二轮指出：颜色重复及顺序含义不明、相近职责缺少区分、战后事实约束容易压住后续叙事。已分别明确颜色互异且顺序无关、补充三组相近职责的作战倾向，并将约束收窄到战斗事实，允许继续人物反应和后续事件。

最终文本再次交同一审阅者复核，确认以上三处已改善。EJS 属于发送前模板：现有渲染测试验证关闭时正文为空，开启时只输出规则正文，不把变量读取及条件包装发送给叙事模型。战斗标识、历史去重、组装规则、字节上限继续由程序承担。标记、JSON、五字段及数组与正文同序保留，它们直接决定入口能否被程序读取。

本轮保留的产品问题：`1d3` 是人数范围还是真实随机、传奇的具体队形、区域等级缺失时的处理、取消或改变遭遇后旧入口何时失效。未替用户设定新的规则，也未把这些状态管理要求移交 AI。六份盲样对应修订前的冻结文本，后续三处澄清及最终文本复核分别保留，不冒称样本最初由最终文本生成。验证和原始证据见 [组装器 v2 记录](sillytavern-enemy-assembler-v2.md)。

姓名和种族由 AI 在战斗块中提供：`name` 填剧情姓名或称呼，`race` 填世界观种族。入口卡、队伍准备、本场战场卡片与详情、图鉴和往昔再现使用这份显示信息；编译、存档恢复和阵容重建完整保留。`race` 为叙事显示字段，与技能实际使用的 `troopTypes` 分离，不参与技能配方、面板随机、选图或能力学习身份。新提示词要求七项齐全；旧消息及旧存档缺少显示字段时保留既有通用称呼。
