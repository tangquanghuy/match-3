## 真实酒馆人工测试入口

独立联调站点：`https://match3-tavern-playtest.linjiang-workshop.workers.dev/sillytavern-install.html`。本轮实测环境为官方 SillyTavern 1.19.0、酒馆助手 4.11.3 与 MVU；其它版本需另外验证。

1. 在已经启用 MVU 的酒馆中，同步本仓库 `docs/mvuzod.js` 的三消颜色与 `三消战果` 字段；部署站也提供 `/mvuzod.js` 下载。不要覆盖玩家已有变量。打开已经有消息并初始化人物变量的聊天。
2. 打开上述安装页，下载“三消战斗与魂片.json”，在酒馆助手脚本库导入并启用。脚本已经填好公开部署地址；酒馆页应出现“三消存档”入口，助手脚本也有同名按钮。
3. 创建当前聊天存档，切换聊天应切换绑定；第四份聊天需手动删除已有档。同一酒馆的不同账号使用各自三个槽位。
4. 由 AIRP／接入脚本将 `StoryPlan` 写入聊天级 `match3.encounter`，结构见 [宿主接入说明](sillytavern-host-integration.md)。点击“剧情挑战”，核对敌人预览并确认；不存在有效遭遇时应显示具体原因。
5. 在准备页选择同伴、装备和主动。没有武器时默认骑士之剑；同伴颜色由“写入同伴颜色”持久化到真实 MVU，取消和刷新后仍保留。当前剧情临时 HP 必须为 0；非零会明确阻断，此缺口尚未完成。
6. 进入从公开站加载的战场，操作宝石匹配和施法。点击“全屏”及“退出全屏”；返回后仍可操作。确认浏览器允许全屏。
7. 实际胜利后核对本场结算的魂片名称、数量和战报：击败对象、我方倒下／复起、初末生命百分比均须与实际一致。败北也记录战报，零魂片且不建胜利图鉴。
8. 核对真实 MVU 当前生命、`三消战果[battleId]` 与聊天级 `match3.storyResults[battleId]`；刷新后奖励与生命不重复变更。从“往昔再现”挑战，敌方配置仍为原场、我方为当前准备配置的满血副本，再现后酒馆生命不变。
9. 重载、停用脚本应清理入口和战场；重新启用后显示原存档。中途刷新目前只支持从该场开局重新开始，尚未达到逐行动恢复。

上述步骤是人工验收清单；实际已通过与待完成范围以 [发布联调记录](sillytavern-release-20261024.md) 为准。学习／装配、淬炼与全档平衡等整版剩余项仍按 STATUS 保留。

## 本地启动与入口

在项目目录执行 `npm run dev -- --host 127.0.0.1`，打开 `http://127.0.0.1:5173/sillytavern-playtest.html`。普通 `npm run build` 也会输出该页面。页面使用独立示例聊天数据，但存档、准备、战场、结算和同步都走正式模块。真实酒馆安装按 [宿主接入说明](sillytavern-host-integration.md) 执行。

## 主流程

1. 页面打开后，在“三消存档”面板创建当前聊天存档。一个槽位绑定一个聊天，最多三个；第四个需要手动删除已有档。
2. 点击“开始示例遭遇”。准备页默认主角单人，无主手装备时使用骑士之剑。核对战斗面板，确认进入剧情战斗；取消不创建战斗。
3. 可选加入同伴：先为同行者选择一或两种颜色并“写入同伴颜色”，再指定基础主动能力，加入队伍并调整顺序。颜色写入示例酒馆变量，取消或刷新仍保留；准备配置随当前存档保存。
4. 在真实三消战场完成战斗。胜利时，本场结算必须显示具体魂片名与数量，并显示完整战报；败北没有魂片或图鉴记录。生命与完整战果回写示例酒馆，页面下方可核对人物状态。
5. 返回存档，在“魂片收藏”查看累计进度，在“往昔再现”展开原场敌方配置并重复挑战。再现使用当前队伍与装备的独立满血状态，敌方完整阵容及规则取原战斗。
6. 再现仅发未学会能力的魂片，酒馆当前生命和临时生命保持。首次剧情胜利计入学习次数；五档依次为 20 / 14 / 10 / 7 / 5。无接收同伴也可收藏；不同来源同能力学会后统一关闭收集，整场全学会后保留查看并关闭新挑战。
7. 使用四个示例聊天验证三档上限、切换原档和手动删除。逐档导出备份，切回原聊天后导入，核对绑定和进度。

## 按机制分类组装与正式战场试玩

1. 在同一来源打开 `/sillytavern.html`，找到“按战术设计敌人”。组装方式默认“按机制分类组装”；保留默认颜色／档位／形态／职责，保持高级效果约束为空，点击“编译战术设计”。程序按主职责与内置权重生成完整主动和特质，显示真实颜色、耗蓝及描述。记录种子与所选战法，换种子再次生成应可获得不同战法；恢复原种子应复现。展开“高级效果约束”后可测试旧的伤害＋减伤约束。
2. 点击“保存完整敌人配置”，刷新页面。组装方式、需求、主动与有序特质、名称、颜色／耗蓝均应恢复。修改等级再保存，模块应保留；切换立绘时若完整颜色／档位兼容，也应保留现有机械配置。
3. 点击“加入本场编队”，可编辑另一个设计再加入，最多四人；尝试换位和移除。点击“保存当前编队”，刷新后核对顺序和每人的主动／特质均保持。390px 窄屏应能编辑、保存并查看完整结果。
4. 打开同一来源的 `/sillytavern-playtest.html`，在“三消存档”创建当前聊天档，再点“挑战已保存的组装编队”。在正式准备页确认当前我方队伍和装备，再进入三消战场，核对敌方为刚保存的完整阵容。该按钮读取已保存的编队，预览中尚未保存的草稿不参与挑战。
5. 在战场核对站位、主动／特质和法力消耗，完成匹配充能和施法。减伤按特质实际作用范围观察，例如骷髅减伤应用骷髅命中验证；眩晕等失能状态按原规则影响特质。战后核对战报及本场实际魂片，胜利进入图鉴，败北不进入图鉴；其后从往昔再现挑战原场冻结配置。
6. 首次未保存编队、保存空编队或编队数据损坏时，按钮应显示明确原因，不创建待完成战斗。准备页取消也不创建待完成战斗。先完成或放弃既有待完成挑战，再开始下一场。

旧设计缺少组装方式时恢复为“原生完整配置”，保持此前来源选择与保存结果。验证某个固定来源时显式选择这个模式；新生成按源主职责固定分池，再按完整战法与特质权重选择；native 新生成保留整套配置，但也使用新选择器，旧种子与固定来源的对应关系只用于历史存档恢复。

职责分类回归可在“原生完整配置”中选择颜色红／黄、首领、类人、Warrior，取消伤害、保留全部破坏，等级 20、难度 1、种子 1。检查实际骷髅产出及职业说明，不把条件增伤解释为必然增伤或自行附加状态。

在已保存有效设计后，勾选全部必需效果再编译；若组合无解，应显示原因，保留草稿和此前保存结果。参考战力、槽位／稀有度限制均可检查，五档强度和武器关系仍需人工标定。运行时 AI 的调用示例见 [宿主接入说明](sillytavern-host-integration.md)，完整模块规则见 [分类组装规则](sillytavern-enemy-assembly-rules.md)。

## 单体与整队预算预验收

在 `/sillytavern.html` 保留默认战术设计，单体上限先留空，编译后查看“同源原生参考战力”。输入单体上限 0 后编译，应显示配方超限及实际值，保留此前结果和已保存配置；清空上限恢复原有候选选择。设置一个足够的明确上限，保存完整敌人配置并刷新，设计表单的上限和结果应一致。

加入一个或多个敌人，查看“本场敌人编队”的整队原生参考战力。把整队上限设为当前总值，应用并保存，应允许边界值；再把它设为总值减 1，应用或保存都应报实际值／上限，之前保存的整队仍保持。恢复足够上限后验证加入、换位、移除、保存和刷新均保留策略；移除最后一人后保存空编队，再刷新并加回成员也应沿用已保存的上限。清空整队上限并保存后可恢复没有此限制的编队。

单体和整队上限分别输入未完成的 `1e` 再编译／保存，应保留输入并提示有效整数错误，已有配置和上限保持；刷新后仍按原上限阻止超限加人。只有明确清空输入并成功保存才移除限制。

参考战力及上限复用原生评分，不代表五档强度、技能联动与武器关系已完成标定。正式宿主提交同一 `budgetPolicy` 时，两种输入路径均应在准备弹窗与待战斗创建之前拒绝超限；再现仍使用原场冻结配置。

## 组装器与派生形态预验收

打开 `/sillytavern.html`，选择带召唤或变形的实际能力。调整等级与难度，核对派生体立绘、生命/护甲/攻击/魔力和主动说明随配置更新；保存刷新后应保留配置。蓝图版本为 3，旧版本提示重新组装。

随机召唤展开完整候选并切到末项，窄屏下仍可操作。其他目标变形的面板是明确标记的同等级示例，实际变形继承目标等级/难度；复制说明使用场上实际来源，不预造结果。召唤继承实际施法者或特质持有者的上下文。

缺立绘的 21 项应同时显示可加载的通用占位图与缺图提示。更换兼容立绘保留能力、等级、难度和数值。派生形态开战预检报错应指出原角色、派生引用与缩放上下文，供玩家开战前调整。本页预览及实际形态播放浏览器测试已通过，环境门和其它特殊宝石触发归属已独立复验；完整视觉体验仍按真实宿主和逐敌人标准检查。

## 1～4 人编队预验收

在 `/sillytavern.html` 选定一个敌人，修改等级或难度后直接点击“加入本场编队”，首次点击就应加入最新配置。再次加入同一来源可使用不同等级／难度，达到四人后加入按钮禁用。各位置显示实际立绘、技能、特质、颜色及数值；首位上移、末位下移禁用。

调整站位、移除成员，核对未保存提示，再点击“保存当前编队”并刷新。位置和完整配置应保持；“清空筛选”及单个敌人的编辑保持编队。草稿只有显式保存后才跨刷新恢复；保存失败保留原保存值和未保存草稿。移除全部成员再保存，只清空编队，不清除已保存的单体蓝图。

基础面板为开战效果前的真实数值合计；各位置分别充能，共享颜色按位置显示。环境召唤基准为开局平均等级向上取整、难度取均值。显式整队上限见上方预算预验收；整场强度与组合协同仍待标定。390px 下可操作排序、移除和保存，页面无横向溢出。

损坏任一成员时应整体提示重组，不静默恢复部分敌人，单体编辑仍可用。普通经济配置可保存和出战；正式开战继续检查实际技能、特质及召唤／派生依赖的完整闭包。本轮定向回归 4 文件 147 项单测、3 文件 26 项浏览器通过，与开头前一轮统一回归不累加；Schrodinger 已独立复验关闭输入直接点击与恢复提示两项首审问题；最终构建、清单与产物检查均通过。

## 原生输入限制与区域条件回归

预览包含选色或选格的能力时，说明应明确只选普通宝石、限定颜色或排除颜色。实际施放时，点击禁止颜色、骷髅或特殊宝石应保留选择态并提示；取消后法力、战场和行动记录保持原值。限定紫色的能力只接受紫色普通宝石。原生技能及组装后的能力共用原有选择器和同一份原生限制。

核对区域条件能力时，场上需同时安排符合与不符合条件的队友；施放后只有符合条件的目标获得附魔、祝福或属性增益。保存刷新后的配置应保留相同条件。本轮自动反例来源为 7029／7079；选色反例为 6139／6263／6961，原生倍率重标后限制传播反例为 7572（技能 9368）。来源 7155 的移除后生成依次使用原生阶段规则，组装 ID 下也应保持相同的宝石结算顺序。

包含输入限制的旧开发配置，其能力内容签名现会反映该限制；恢复时若提示配方变更，重新组装并保存。此项没有添加存档迁移。原生／组装对照使用相同等级、难度、站位、随机种子及职责上下文；通过首次施放对照不代表所有后续回合、随机分支或逐源完整验收已通过。

## 特质说明预验收

组装预览的特质说明来自适配后的实际字段。核对触发时机、目标、概率、数量、属性及召唤引用；保存后刷新，说明和审计提示应一致。经济／PvP 特质已补齐适配后机械说明：主说明简短，完整条件默认折叠在“详细规则”，展开后应显示归属、触发、倍率、上限和适用阶段；单体和编队都应一致，390px 无横向溢出。未识别字段仍须显示待核对诊断。PvP 专用战后结算的适用阶段单独说明；说明完整或战斗资源记录本身不代表持久奖励已发放。

目前独立特质说明结构完整 802 项、待核对 0 项、仅含受限机制而省略 8 项；新增 17 项说明已由 Schrodinger 独立签收，可读性 P3 补修已独立复验关闭。束带同队计数已补混编回归；随机吞噬目标、首次占位光环、来源色/产物色和风暴首色按当前引擎规则显示。此统计只作为说明结构证据，完整战斗行为及数值体验仍按逐敌人标准验收。

## 原生战中资源与再现奖励

普通战中金币、灵魂和地图的生成、消耗、窃取、余额读取、收益倍率与上限，直接使用原三消引擎。四／五连仍有原生金币收益；双方金币分别归属，原生共享资源继续共享。准备页中的普通经济能力与武器可选择，随机召唤保持完整候选池，不要求单个技能同时具备产出和消耗。可用性检查仍会拦截真实缺失的技能、特质、召唤模板及派生依赖；PvP 专用战后货币结算仅在 PvP 请求中受限。

人工检查一个含生成、消耗或读取余额的配置，确认开战、施放及双方归属遵循原三消表现。返回再现结算时，实际奖励只包含本场未学会能力的魂片；战斗内余额不自动兑换为存档货币或材料。重复提交同一结算应返回同一收据，不重复发片。历史收藏、已学能力和旧配置均保留。

## 中断与失败

- 战斗中返回存档，尚无终局时保留开局快照；面板“重新开始”从本场开局恢复，不恢复到中途行动。
- 保存战果失败且已经暂存时，可以返回或刷新，再从“待保存战果”保存。实际已结算的奖励仍按原收据展示，再次重试不加第二份。
- 终局尚未持久化时可导出本场战果。存档备份与战果备份用途不同：恢复结果要求原始战斗对应存档存在。
- 剧情同步失败保留队列；原聊天、原消息/swipe和冻结变量状态一致时可重试。变量冲突不会覆盖新的角色状态。再现不写剧情变量。
- 队列未处理时拦截删除、放弃与新战斗，避免丢失实际结果。

## 当前测试边界

临时 HP 大于零的剧情角色暂未接入独立吸收池；再现仍可测试。人物转换系数未完成体验标定。原生酒馆技能、效果、族群、词缀、武器淬炼尚待后续接入；默认同伴主动与武器映射使用现有目录。真实酒馆中的 AIRP 遭遇消息还需调用公开 `playStory` 接口接线。本地流程通过与真实酒馆安装通过分别记录。

## 同技能单位的每场使用次数

以来源 6486（SandScuttler）组装含两个同技能单位的队伍，敌方也放入该能力。其技能按每名单位分别限制为每场一次。敌方施放后，我方两名单位仍各可施放一次；第一名我方单位施放后，第二名仍可施放。核对每次施放的生命、生命上限及护甲均增加该单位魔力 + 20。补满已使用单位的法力后，重复施放仍应被拦截；AI 应能使用另一名尚未施放的单位。

核对卡面高亮与施放入口一致：已使用单位再次满蓝也不亮起可释放提示，未使用单位照常亮起；敌方使用不影响我方同技能单位。检查回合末刷新与法力入账动画两条路径。

此项浏览器自动检查覆盖真实 App 的施放判定、实际卡面样式及法力入账事件；完整编译、战斗执行和 AI 行为另有集成回归。自动检查通过注入战斗状态核验入口，不代表完整鼠标施放流程。召唤、复制、变形及复活后的次数语义按原生规则和独立审查结论核验。
