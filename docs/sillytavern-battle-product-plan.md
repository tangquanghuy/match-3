# SillyTavern 通用三消战斗：产品与实施方案

日期：2026-10-19；最后修订：2026-10-25。状态：产品规则与实施方案；本地基础战斗流程已接入，真实酒馆接线与整版验收进行中。各任务交付和验收以执行状态为准。

执行入口：[推进计划](../tasks/active/TASK-SILLYTAVERN.md)；当前进度：[执行状态](../tasks/active/STATUS.md)。推进计划承接本文的产品规则，按 P0～P3 拆分交付、依赖和验收。

本文接替接入调研中的产品建议。实现以本文确定的产品边界为准；原始数据事实仍见 [接入调研](sillytavern-progression-bridge-research.md)。本方案不启动云端账户、业务服务器或另一个三消仓库。已按用户要求修正：现有立绘复用是首版硬需求，抽象图形不作为替代方案；族群抽象、技能适配和立绘打标共同组成敌人组装器。

## 1. 产品定位与首版范围

产品是嵌在文字冒险里的可交互战斗模块。酒馆继续拥有故事、人物身份、叙事装备和原生 DND/AIRP 规则；三消模块提供战斗、武器附加能力、同伴技能装配和战后成长。

产品主循环：剧情遇敌 → 玩家选择战斗方式 → 三消战前准备 → 战斗 → 本场结算与技能学习进度 → 战报回到酒馆 → AI 根据事实继续叙事。剧情遭遇通过三消战胜后，可在前端进入「往昔再现」，不重复刷 AIRP 剧情；学会该场所有可学能力后不再开放刷取。原生 AIRP 的胜利不解锁三消图鉴。

采用以下默认设计，不要求用户为中式、日式、西幻分别开发规则或资源适配：

| 项目 | 首版产品决定 |
| --- | --- |
| 世界观 | AI 先提供法力颜色、稀有度、形态和既有职责；特质与技能规则后续扩展；关系代码只用于连续性，不传叙事种族名、职业名或外观正文 |
| 显示 | 每名敌人展示从现有资源选出的真实立绘，附编号、职责和威胁标记；由稀有度／档位（rank）、形态（form）、队伍职责（role）三个视觉维度共同筛选；法力颜色单独作为机械配置 |
| 队伍 | 玩家最多 4 个在场角色，使用酒馆已有主角与同行者，不通过抽卡更换人物 |
| 技能 | 每个角色 1 个主动能力；主角来自武器，同伴来自基础能力或已解锁魂片能力 |
| 成长 | 酒馆等级负责纵向基础成长；三消主要增加能力选择、淬炼和战术组合 |
| 存档 | 游客模式；一个槽位绑定一个酒馆聊天，本地最多保留三个聊天存档；酒馆变量持久化同伴颜色与聊天绑定引用，宿主所在 origin 的 IndexedDB 持有对应三消存档 |
| 运行 | 一个仓库共享战斗引擎；增加通用战斗入口与酒馆端薄桥接脚本/扩展 |
| 接入 | 正则负责识别战斗块和展示入口；桥接脚本负责变量、通信、存档和回传 |

首版围绕普通遭遇、精锐、单首领战斗打通闭环。守点和限时战可复用现有规则，排在基本闭环之后；多波次、独立多技能槽和首领阶段系统后续增加。现有一个主动技能里的多段效果可以正常保留。

交付口径：P2 是可灰度试玩的战斗版本，P3 是包含魂片和淬炼的首个完整产品版本。以下首版养成设计在 P3 交付，不把它写成 P2 已有功能。

## 2. 玩家实际看到的流程

### 2.1 首次启用

玩家在现有开局配置页选择“三消战斗模式”，由 MVU `stat_data.系统配置.三消战斗模式` 布尔字段持久化，默认关闭。之后可在底栏系统设置切换。开启时底栏显示“三消”入口，直接懒加载共享面板模块；存档创建和管理纳入该面板。酒馆助手与 MVU 沿用角色卡既有依赖，独立存档助手脚本只保留兼容联调用途。现有立绘与通用设计词表随模块提供，玩家无需为每个世界观重建图库或编写种族适配代码。

桥接程序按当前酒馆聊天查找唯一绑定存档；已绑定则加载，首次打开面板时未绑定则自动为当前聊天创建新档，占用三个槽位之一。槽位已满时先展示存档管理页，由玩家手动删除旧档后再创建。随后读取主角和同行者的现有变量，给尚未绑定的装备登记稳定能力代码。同行者超过 3 人时，玩家选择本场出战者；不静默删人，也不把未出战者的 HP 改成战斗结果。

首次为同伴配置可用的基础能力；主角没有武器时使用现有最低稀有度默认武器「骑士之剑」，具体见 6.1，保证玩家不必先刷魂片才能开战。断网可运行以静态资源已缓存或本地服务可用为前提；不把“无业务服务器”误写成“任何时候都能离线访问远端网页”。

关闭模式前检查当前聊天的待完成战斗及待保存战果；已有战斗先完成结算或显式放弃。刷新后也从持久数据库检查。模式关闭保留原档、魂片和图鉴；切回原聊天继续原档。

当前实现进度：开局/schema/底栏/管理面板已接入；下节正文战斗块及完整 AI 可见战报仍待实现，不能用变量 API 闭环代替此验收。详见 [协议对齐审查](sillytavern-protocol-alignment-20261024.md)。

### 2.2 剧情遇敌

AI 在正常叙事之后或中间附带抽象战斗块。叙事中仍可写敌人的名称和外观，但这段正文不发送给敌人组装器。

酒馆将战斗块渲染为一张折叠卡，显示「准备战斗」。卡片尚未开始时，可以选择三消或沿原生规则处理；切换选择只发生在开战前。

敌人编号按当前遭遇中的引用固定，卡片与战报始终使用 E1、E2 等编号。AI 在自己的叙事上下文中保留哪个编号对应哪个人物，不把名字额外复制到战斗协议中。历史引用随原消息保留，方便恢复上下文；上下文遗失时读取原消息，不让战斗引擎猜身份。

### 2.3 战前准备页

页面只保留四块信息：

1. 我方出战角色：槽位、当前生命比例、颜色、主动能力、队列顺序。
2. 敌方情报：实际立绘、E1/E2、形态、职责、个体档位、当前可见的能力与被动效果；需要时展开族群关系。
3. 本场条件：人数、胜利目标、地区/遭遇给定等级和总体危险提示。
4. 操作：调整顺序、装配已解锁能力、淬炼、开始、返回。

敌人组装和颜色在第一次受理本场时固定。重新打开准备页不会重新抽技能、立绘、掉落或颜色。不能通过反复刷新刷出更弱的同一遭遇。

准备页允许修改我方配置；按「开始」后冻结双方配置、ST 变量基线、规则版本与随机种子。本场不能中途换装备或切成 DND 继续算剩余伤害。

### 2.4 战斗页

复用现有棋盘与角色卡，不进入王国地图、招募、收藏抽卡、活动商店等原生 meta 页面。

敌人卡以实际立绘为主体，叠加编号、职责、个体档位与关键敌人标记。图片由组装器从已打标资源中解析，不能让渲染器用能力 ID 或名字反查原生部队并带回一套固定身份。六色始终只叫红、蓝、绿、黄、紫、棕，不自动等同于火、水、自然、神圣或其他世界观属性。

卡片详情使用机械描述，例如「对单体造成伤害，并使其下次主动能力失效」，不显示原目录的部队名、王国、官方技能名或带叙事色彩的特质名。描述必须由实际编译后的效果生成。

### 2.5 本场结算页

固定展示：三消胜负与撤退、实际击败的敌人、我方曾倒下成员及其是否复活、各参战者入场和结束时的生命百分比与净变化、本场实际发放的材料与货币的真实名称和数量、每条魂片进度的变化、解锁的能力，以及「返回酒馆」；再现结束返回魂片图鉴。所有奖励读取本次结算账本，不在页面重新抽取，首胜和里程碑只展示本场确实入账的数额。

结果先在本地落盘，再同步到酒馆变量和消息上下文。同步未完成时显示「结果已保存，等待同步」，允许重试同一结果。同步完成后，AI 在下一次续写读取报告；首版不强制自动触发一次新的模型生成。

### 2.6 战斗外养成页

单独提供「队伍 / 武器 / 能力（含魂片与往昔再现） / 战报与存档」四个入口，能从战斗准备卡或酒馆工具栏打开。养成页只管理三消附加状态，角色是否入队、武器是否穿戴仍以酒馆变量为准。

## 3. 敌人设计器：三视觉维度选图与法力配置，再扩展特质与技能

当前确定的设计入口保留法力颜色、稀有度、形态、队伍职责。已有立绘只按稀有度／档位（rank）、形态（form）、队伍职责（role）三个视觉维度严格相交选取；法力颜色（manaColors）作为独立机械配置。运行时 AI 使用有含义的分类，叙事姓名、具体种族名、具体职业名及外观正文留在酒馆上下文。等级和引用字段另行承载。

### 3.1 三个视觉维度与法力颜色字段

| 字段 | 选项与来源 | 作用 |
| --- | --- | --- |
| manaColors | 红、蓝、绿、黄、紫、棕的颜色集合；遵循档位配色和原生机械契约 | 用于充能与机械组装校验，独立于立绘来源；不参与选图，也不解释成某世界观的元素 |
| rank | 杂兵、精锐、首领、领主、传奇 | 按当前项目实际稀有度映射立绘定位 |
| form | 人形、野兽、类人、怪物、异形体 | 按成图主体形态匹配 |
| role | 坦克、输出、供魔、辅助、法师、术士、刺客、战士、统帅 | 复用项目现有 role 标签及中文词表 |

人形与类人的区分以实际面部为准：人脸与人形身体，即使带兽耳、尾巴或角，仍是人形；类人是身体接近人形而脸明确为非人面孔。遮脸不是非人面孔的证据。人面但人马、鱼尾、蛛身等复合躯体归怪物。详细判定和数据见 [立绘形态标注](portrait-forms.md)。

稀有度映射按项目显示档位：普通/精良 → 杂兵，稀有 → 精锐，传说 → 首领，史诗 → 领主，神话 → 传奇。代码键实际为 Common/Uncommon、Rare、UltraRare、Epic、Legendary；不得将 Legendary 直译为传说而错配。等级与稀有度分开，高等级杂兵仍可强于低等级传奇。

档位配色保留：杂兵单色，精锐／首领／领主双色，传奇三色。等级参考当前区域和任务难度，不与玩家等级绑定；3 个及以上同类型敌人须混合不同兵种，保留集群战术要求。上述规则独立于立绘选取。

### 3.2 职责复用与资源组合约束

职责从 src/meta/data/roles.ts 取现有九类：Defender/Striker/Generator/Support/Mage/Warlock/Assassin/Warrior/Warmaster。图片不新增 roleHints，不根据画中器具、动作或服饰另造一套职责。

rank/form/role 三个视觉维度严格相交，只有有图的组合才是可用视觉入口。同一组合可以有多张图，由前端稳定选图并保存到蓝图。没有候选时返回 no_exact_match，保留稀有度、形态和职责的严格约束。manaColors 不参与选图，有图也不代表所选职责与配色存在可执行配方；机械组装另行校验并保留实际诊断。

运行时 AI 在战法上只选择主职责 role，效果与机制组合由分类组装器按职责及程序内置权重生成；旧协议显式效果约束继续按兼容规则验证。分类组装器按完整主动与独立特质的实际效果、法力颜色／成本、来源稀有度和槽位选择模块。主动技能的法力配色、充能费用与效果公式仍遵守原生契约，候选须满足相应配色与职责约束。源 role 仍约束立绘定位，机械职责由可执行效果验证。五档强度、复杂度及武器关系继续通过实际战斗标定；立绘覆盖与机制行为验收分别统计。

### 3.3 后续协议的最小示例

~~~json
{
  "level": 18,
  "manaColors": ["Blue", "Purple"],
  "rank": "首领",
  "form": "人形",
  "role": "坦克"
}
~~~

这个示例只表达敌人的等级、法力颜色、稀有度、形态和队伍职责。当前协议不要求运行时 AI 提供对象 ID、蓝图 ID、立绘文件名或源部队身份；这些都是程序在接受设计、选图和落盘时生成的内部数据。它是待接入的设计契约，不是已经可直接发送给 BattleRequest 的字段。当前离线工具支持这些中文分类以及原有英文颜色、职责键。

AI 不填写源部队名、具体种族或立绘文件名。程序从 rank/form/role 三个视觉维度的相交候选里选取立绘，后续按独立的法力配置组装技能与特质；选图不自动继承源部队的具体身份或整套能力。

### 3.4 提示词和编译器使用同一份语义规则

提示词模块提供：各分类的含义、职责签名、档位限制、可用形态、可选特性、合法组合与少量范例，以及当前相关角色和蓝图的引用。它是酒馆提示词内容，不要求模型调用 Codex 的 SKILL.md。无需把几千条技能或整份图片标签常驻注入。

首版单次提交：语义设计 → 规则与组合校验 → 已适配技能检索/配方编译 → 预算校验 → 真实图片解析 → 准备页预览。候选与详细内部 ID 留在本地，不先要求第二次模型调用。

未知枚举、冲突职责、超预算或没有真实图片的主要结构组合，返回能说明原因和可行修改的语义错误。新消息由 AI 选择主职责，效果由程序生成；旧消息显式声明的必需效果须满足，只有明示可选的偏好才能放宽。玩家也可在准备页改为已验证的基础方案。

协议规范、提示词说明和校验错误从同一份设计词表生成。测试除成功编译外，还要检查：坦克方案实际符合职责规则；杂兵与传奇遵守各自复杂度上限；人形不会解析为四足图；提高剧情权重不会暗增面板；相同种子重现相同结果。

### 3.5 族群联动暂不进入本阶段协议

形态分类与具体族群是两件事。当前先解决五形态和立绘复用，不把源项目的种族、王国或族群关系塞进通用协议。等技能和特质规则确定后，再为确实需要族群联动的机制设计关系字段；在此之前，AI不提交 `lineageRef`、`sameLineageAs` 或阵营 ID。

### 3.6 组装结果统一保存为持久蓝图

组装结果保存：有语义的设计分类、已声明的族群/阵营关系、实际技能与被动、颜色和成本、面板预算、内部图片配方及真实资源绑定。内部可以使用机械配置 ID 和视觉配方 ID 管理数据，它们不替代 AI 的语义输入。

重复遭遇复用蓝图；等级和明确允许的展示变体单独变化，能力、族群及学习来源不每场重抽。主动、被动和特性有重复效果时按实际叠加规则合并计价。

预览台必须验证：相同职责在不同形态下仍有相同战术核心；相同形态可组装不同职责；同族换图仍触发联动；异族共用图片不触发同族效果。每个正式敌人都解析到真实图片。

## 4. 几千条技能如何真正进入通用引擎

### 4.1 全量入账，分路径适配

先对部队技能、武器技能和关联特质建立去重清单。部队条目数、不同 skillId 数、武器数不能直接相加当作唯一技能总数。每个清单项都必须有以下一种状态：

| 通用状态 | 处理方式 | 例子 |
| --- | --- | --- |
| 可直接使用 | 复用已验证原型，生成中立机械描述 | 不依赖固定对象的伤害、恢复或普通状态 |
| 需绑定上下文 | 用版本化规则绑定抽象关系、对象、颜色约束 | 指定同组加成、召唤对象、变形目标 |
| 需专门适配 | 增加可复用的通用机制实现，再开放该类配方 | 复杂跨段目标、特殊条件或世界依赖 |
| 现阶段不可用 | 记录真实原因，不进入通用候选池 | 缺失实现、空原型或无法保持语义的项目 |
| 范围外特殊机制 | 列明实际外部依赖与排除依据，单独统计 | 依赖晋升度、淘宝模式、魔头专用机制的技能及敌人配置 |

所有条目都要有处理结论；“引擎注册了原型”不等于“通用模式可以直接使用”。这次建立的是通用适配索引，不重新启动已完成的旧技能审核任务或恢复其历史审查台账。

### 4.2 打标内容

从现有原型结构自动提取：目标、效果段、缩放来源、条件、时序、颜色读写、资源、额外回合、引用对象与分支。原目录的职责只可作提示，最终职责必须结合可执行效果确定。

索引额外登记四类数据：

1. 战术能力：满足哪些现有 role 与后续 effects/target/tempo。
2. 战斗成本：基础强度、控制占比、复杂度和组合禁忌。
3. 上下文依赖：种族/王国/固定 troopId、外部对象、召唤表、经济与稀有度条件。
4. 展示映射：从实际效果生成中立名称、准确机械描述与报告事件类型。

无法确定的内容进入一个精简的待适配清单，修正生成规则或显式覆盖数据；不要再铺几百份技能任务书。产物是一个可重复生成的索引、一份覆盖统计和少量必要覆盖配置。

### 4.3 固定联动的去世界观方法

不能只隐藏种族文字。原技能里仍然可能按 Knight、某王国或固定部队 ID 执行，隐藏名称并不会消除机械依赖。

通用变体应把这种依赖显式改为抽象关系：例如“同种族友方加成”绑定同一 lineageRef，“同王国”类关系按机制含义绑定独立 affiliationRef，“召唤某指定部队”改为绑定某个通用召唤蓝图。族群和阵营不得混作同一维度；绑定规则由设计器声明并校验，不能简单给所有对象伪造一个 GoW 种族，或把相关条件全删掉。

适配后得到的是版本化通用变体，需要重新计算成本和生成描述。原生技能保持原定义，两个模式共用执行器；ST 变体以独立派生代码引用原始来源，不修改原型共享对象。

派生形态的缩放归属固定为：主动／特质召唤继承施法者／持有者，普通变形继承被变形目标，复制继承被复制形态自身上下文。战场传送门归实际触发方，采用开战时该方初始队伍平均等级（向上取整）和平均难度，全场冻结；缺少旧字段的成员按等级 20、难度 ×1 计入。换位、阵亡及后续召唤／复制不改变该基准；预检、实际运行和再现共用此规则，并纳入配方签名，旧签名提示重新组装。正式混合难度编队的平衡标定仍待验收，不把规则一致性视作强度预算已通过。

### 4.4 组合器的工作方式

2026-10-24 用户纠偏：交付对象是运行时 AI 使用的统一分类规则组装器。开发与验证按技能家族、特质家族和组合约束推进，不为 1821 个敌人分别手写配方、测试和签收。原敌人目录用于自动导入、规则覆盖统计及回归样本。

AI 提交颜色、稀有度／档位、形态、主职责与等级等语义条件，战法只选主职责；程序按职责及内置权重生成效果，分类、筛选并装配主动与特质，绑定真实立绘及必要上下文，校验后生成持久蓝图。AI 不提交原敌人编号或内部组件代码。优先复用完整原子主动，保留其目标锁定、效果顺序、分支和概率；需要组合多个效果段时使用已验证的受约束配方，最后仍生成一个主动技能。原生执行器继续复用。

主动分类覆盖伤害／真实伤害、状态控制、属性增减、治疗净化、供魔、造石转色爆破、召唤变形、吞噬、条件／概率／分支；特质分类覆盖开场增益、免疫减伤、充能、匹配／受击／死亡等触发、族群与编队联动。目标关系、时序、资源读写、上下文依赖、收益与副作用作为组合约束，不能只把技能压成一组效果标签。固定联动保留为有依赖声明的组件组，不强行拆散。

装配结果按实际主动与特质共同验证职责、必需效果、颜色成本、适用档位、依赖绑定、派生闭包和单体／编队预算。立绘另按 rank/form/role 三个视觉维度严格匹配，法力颜色独立进行机械组装校验。相同设计与种子复现完整配置，刷新与再现保留该配置；学习身份继续按实际机械能力去重。具体数值预算使用实际标定结果，尚未标定的部分明确列为缺口。

验收按机制家族的独立代表案例、交互边界与整队端到端场景验证共享规则，再通过全目录自动检查计算各稀有度／五档至少 90% 的适配覆盖；规则缺失会自动影响所有依赖该规则的目录条目。详细口径见 4.5。

### 4.5 敌人覆盖率与特殊机制排除口径

覆盖对象是现有敌人目录中的独立敌人条目，以稳定目录引用去重计数。相同技能被多个敌人使用时，验证共享机制规则，并自动映射到各敌人分别统计；不要求为每个敌人另写测试或独立签收。配方数、图片数、索引登记数、规则家族验证与敌人覆盖率分别报告。

各稀有度覆盖率 = 已通过完整组装验收的适用敌人数 /（该档敌人总数 − 明确排除的特殊机制敌人数）。各档分别满足通过数至少为适用敌人数乘 90% 后向上取整，整体平均值单列。按原始各稀有度逐档出表，同时按通用五档汇总，保留普通与精良等合并前的明细；适用数为零的档位标记无适用对象并展示依据。

每档报告总数、特殊机制排除数、适用数、已通过数、未通过数和覆盖率；由程序逐条输出来源、依赖的主动／特质／目标／上下文规则、组合校验结果及缺口原因。规则验收覆盖代表机制、参数边界、效果顺序与关键交互；目录自动检查覆盖字段完整性、已验证规则归属、真实立绘、编译／派生预检和持久化契约。任一必需规则未知、未验证或组合不成立，对应条目记为缺口。完整组装通过要求真实立绘绑定、主动与适用战斗被动/特质、目标、法力成本、颜色、缩放和上下文依赖可正确编译并执行，且说明与实际效果一致。通用化转换保持原机械语义，不带入原世界身份。对仅完成索引、使用占位技能、遗漏关键效果或依赖缺失的条目，保留在适用分母并记为未通过。

范围外仅按实际外部依赖登记：晋升度、淘宝模式、魔头专用机制等。先按技能/特质登记排除，敌人其余独立的普通能力继续适配；仅当主要战斗配置依赖范围外机制且没有适用配置时，才将该敌人整条列入排除分母的清单。排除清单记录对应技能、敌人及依赖证据；技能复用时逐条关联，避免只按名称匹配。普通等级/稀有度、普通首领战以及通用召唤、变形、控制、族群联动仍属于适配范围。实现复杂或尚未适配的普通机制计入缺口；为达到每档 90% 所需的机制在 P1 完成。其余适用缺口保留清单，在后续版本继续扩展。

## 5. 固定同行者与灵魂碎片

### 5.1 我方角色不等于原生部队卡

主角和同伴都是酒馆里已经存在的角色，通过稳定 memberRef 引用。同行状态、等级、基础属性与当前生命由酒馆提供；不会因为选三消而变成 GoW 部队，也不使用其收藏升阶、重复卡或王国加成。

我方首次初始化也使用相同的职责、形态和特性词表，按需声明族群关系，程序保存 memberRef 与设计配置。后续敌人的同族光环、种族克制才能匹配已声明身份；不能只给敌方登记族群而让我方永远没有可匹配身份。

每个同伴首次初始化得到一种或两种稳定颜色和一个基础能力，按抽象职责分配。颜色写入酒馆侧对应角色变量并持久化；已有颜色时直接读取，三消前端按本场读取值冻结配置，不因重新打开页面、装配魂片能力或 AI 重新描述职业而重抽。颜色表示充能方式，不表示种族或法术属性。

同伴只有一个当前主动能力，装配魂片能力就是替换它；可以免费切回基础能力。战前免费装配，战中锁定。原有 AIRP 技能树、资源技能和特质照常留在酒馆，不因替换三消能力而增删。

魂片收集与当前是否有装配对象相互独立。单人冒险、没有同伴或当前同伴均不兼容时，仍可正常收集、推进学习并解锁能力，作为本聊天存档的收藏保留；以后有兼容同伴再装配。同伴离队不移除已收集进度或已学能力；保持主角使用武器能力、同伴使用基础或魂片能力的分工。

### 5.2 魂片进度究竟累计给谁

魂片来源由宿主在接受敌人设计后自动建立内部蓝图记录，但此时只是候选记录；只有该剧情遭遇的三消战斗实际结算为胜利，才开放对应图鉴条目与再现入口。原生 AIRP 的战果不用于解锁。运行时 AI 只提交本次敌人的颜色、档位、形态、主职责和等级，技能效果由程序生成，不提交对象 ID 或蓝图 ID；程序负责把本次设计与后续重复遭遇、能力版本和魂片进度绑定。等级可以按遭遇变化，但已经登记的能力和魂片来源不能每场重抽。

如果仅凭“输出/控制”等职责相似就合并进度，会把不同敌人误认为同种对象，因此不采用。剧情再次遇到同一敌人的归属仍需根据已有引用或玩家确认；失去引用时可读取之前的消息，或由玩家在图鉴里合并来源。程序无法从同一套抽象战斗参数可靠反推出物种。往昔再现直接引用已记录的遭遇与蓝图，不重新请 AI 判断是否同源。

同一蓝图不同能力版本分别保存，已经积累的进度仍指向原能力版本。普通升级不悄悄改变玩家正在学习的技能。

同一聊天存档的已学能力按实际能力配方统一登记，与敌人来源分开。任意来源学会某能力后，所有给出相同能力的来源立即视为已学会，包括之后新发现的来源；停止相同能力的魂片获取，不重复学习或转换材料。相同能力以已登记的实际配方为准，叙事名称、敌人稀有度、等级和图片不同不构成新能力；实际效果、颜色成本或绑定条件不同的变体分别登记。尚未学会时各来源保持自己的稀有度门槛和进度，不把不同来源的点数相加；任一来源达到门槛后统一标记学会，结算页只显示一次能力解锁。能力与进度只在本聊天存档内共享，其他聊天独立。

魂片按敌人来源展示，结算与收藏使用原战斗记录中的敌人姓名，例如「遗迹守卫的灵魂碎片」。技能效果名、公式和内部配方指纹不作为碎片物品名；学习仍按原来源进度及实际能力配方登记，不因显示名称相同而合并。能力名称和效果在能力信息中单独显示。旧收据保留入账记录，查看时从该收据对应的原遭遇来源和敌方快照解析名称，不从当前队伍或技能文本猜测。

### 5.3 进度与装配规则

以下数值是首轮体验测试起点，以来源蓝图的稀有度确定解锁所需胜利场次，需要模拟与实玩调参，不作为现有数值结论：

| 项目 | 首轮建议 |
| --- | --- |
| 稀有度：杂兵 / 精锐 / 首领 / 领主 / 传奇 | 各来源约需 20 / 14 / 10 / 7 / 5 次三消有效胜利；不按等级、威胁或同场数量倍增 |
| 每场胜利的进度 | 本场实际有效击败且能力尚未学会的每个独立来源 +1；同一来源出现多个敌人也只计一次 |
| 剧情首次胜利 | 三消胜利解锁图鉴，并计入实际有效击败来源 +1；原生 AIRP 胜利不解锁图鉴、不发三消魂片 |
| 学会能力 | 任一来源达到需求即解锁配方，所有相同能力来源均标记已学会并停止掉片；不需要再支付额外学习材料 |

魂片只奖励三消剧情胜利或再现胜利，以本场冻结的原敌方阵容和实际有效击败记录逐来源结算；剧情首次胜利的图鉴解锁与 +1 在同一次结算完成。仅在阵容中出现而未被有效击败的敌人不贡献魂片。败北、撤退、无限召唤物和重复结算不给学习进度；剧情增援默认不计，只有事先并入可复用遭遇阵容且有独立蓝图的对象才成为来源。各来源的需求和进度独立，已学能力状态按 5.2 在同一聊天存档内统一。

“同色可装”体现为：成员颜色与能力学习颜色匹配，并通过该能力声明的兼容颜色组合与成本规则。只改变颜色显示是不够的；技能如果固定读写某色棋盘资源，必须使用已验证的颜色变体，否则不进入该成员的可装列表。

解锁得到的是能力配方，不是敌人的高等级伤害数值。装到同伴身上时，按该同伴的等级与当前面板计算。没有二次随机技能，也不附带替换人物身份。

配方引用需要区分“施法者同族”和“明确指定族群”。前者在装配时绑定装备者当前族群，后者保留已登记的克制/召唤对象；不能把原敌人的全部族群身份复制给学习者，也不能让更换技能把同伴改成另一种族。所有变化重新通过同族联动与预算检查。

### 5.4 往昔再现：在三消前端补齐魂片

「能力 / 魂片」页只列出已通过三消战胜的剧情遭遇来源：真实立绘、rank/form/role 三视觉分类与独立法力配置、可学习能力的机械效果、当前进度与解锁需求。相同能力已从其他来源学会的条目直接显示「已学会」。每个来源可查看对应已记录遭遇的「往昔再现」；进入前预览完整敌方阵容、固定挑战等级、胜利且有效击败时各未学会来源可得的魂片 +1，以及还需几场胜利。剧情三消败北、撤退、尚未开打、仅受理了蓝图，以及选原生 AIRP 获胜，均不解锁图鉴或再现。三消胜负直接取本场战斗引擎实际结果，与敌方击败记录、我方倒下/复活情况和生命比例变化一并保存。剧情战斗未结束时暂不开放再现。

每场再现重打当时那场剧情战斗的完整冻结配置：原敌方人数、阵容与槽位、蓝图、能力版本、真实立绘、等级及难度规则，不拆成单敌挑战，也不重新调用运行时 AI、随机组装敌人或按视觉分类或法力配置碰巧相同就合并来源。玩家以当前已登记的三消队伍和装备进入，但使用本场独立的满血战斗快照，不读取或扣减 ST 的当前/临时 HP。未来若开放升档挑战，必须单列模式及其奖励，不自动改变原能力的来源或学习版本。

每次点击挑战创建新的战斗 ID；胜利后该场每个实际有效击败且能力尚未学会的独立来源各得 +1，不因同种敌人重复出现而增加，同场各来源独立累计。任一来源达到门槛，立即解锁能力并把其他相同能力来源一并标记为已学会。混编战只要还有未学会能力，就允许以完整原阵容再现；原阵容中所有可学能力均已学会后，关闭该遭遇的挑战入口，仅保留图鉴和「观看重放」，即使某些来源自己的进度尚未满也不再开放。失败、撤退和同一战斗 ID 重复提交不发胜利奖励。再现首版仅产出未学会能力的魂片，不发淬炼材料、学习材料、剧情首胜、高档首胜、里程碑、ST 经验、通用币或叙事战利品；后续材料刷取须另行设计获取模式。首版不设每日次数或入场券。

再现结果只进入绑定当前酒馆聊天的唯一存档，在本场结算页展示实际入账的每个来源魂片名称、数量、进度与本次解锁能力；无其他奖励时不伪造奖励卡。不回写 ST HP、不生成新的剧情战斗结果、不自动让 AI 续写一次“又遇见敌人”。历史战斗的「观看重放」只读旧日志，不创建新的挑战 ID，也不发奖。图鉴区分「挑战再现」和「观看重放」，并显示该来源还差几场或能力已从其他来源学会。P2 起保存剧情三消的冻结战斗配置、实际胜负、击败名单、倒下/复活记录与生命比例变化；P3 只对其中三消胜利的记录开放图鉴与再现，旧记录无需重走剧情，原生 AIRP 的战果不用于补录解锁。

## 6. 武器绑定、淬炼与获取

### 6.1 叙事武器与三消能力分开持久化

主角没有武器时，三消侧固定使用现有最低稀有度 Common（rarityIdx=0）的「骑士之剑」（gw_KnightsSword，目录 ID 1000）作为默认武器，沿用其蓝色法力、3 点充能成本及现有主动能力；与项目现有 STARTER_WEAPON_ID 保持一致。默认配置用于三消附加层，无需生成酒馆叙事装备；有实际装备的武器时使用该装备的稳定绑定，卸下或失去武器后回到默认配置，战中保持本场冻结配置。

ST 装备仍拥有原名称、品质、描述和强化字段。新增装备时，程序为该装备实例登记一次武器能力代码；默认由装备品质档和中立能力偏好筛选，候选只来自已适配目录。之后不会因为打开 iframe、提示词刷新或角色改名重抽。

建议保存装备实例 ID → 能力代码的映射。底层代码仍可指向现有 gw_*，AI 侧需要引用时使用不透明别名。任何会进入提示词的变量必须经过序列化白名单，不能把 gw_* 的原始英文名称和整份目录对象直接注入。

武器页显示本地登记编号、颜色、精确能力说明和淬炼；叙事名称不属于组装必需字段。玩家可手动设置仅用于自己界面的备注，不回传敌人设计器。删除或丢失叙事武器不会自动生成一把新的同名三消装备。

### 6.2 萃取机制

新获得的装备带来一个已适配的能力代码。玩家可以把该能力登记到自己的能力库，并消耗中立材料绑定到另一件合法品质档的叙事武器上；不改变该武器的 AIRP 伤害骰、强化等级或叙事品质。

同一件装备实例只提供一次首次登记奖励，删除后重新注册不能重复领取。重复代码可转换为淬炼材料。首版只开放“保存代码、首次绑定与淬炼”；萃取/重绑在基本存档和唯一实例识别可靠之后开放。

### 6.3 淬炼

复用现有 forge.ts 中的上限、逐级成本与词缀解锁规则；按通用能力代码保存淬炼等级，同一代码对应的装备共享进度。萃取后进度仍跟能力代码走，避免装备实例来回切换丢失投资。

首版不继承武器目录的固定攻击/护甲/生命面板来覆盖 ST 基础属性。淬炼的永久基础面板增量转成有上限的三消内加成，建议每项累计不超过该角色未淬炼基值的 20%；没有基值的项目不能凭淬炼产生大量额外属性。+6 之后保留经通用适配的词缀，词缀强度单独计预算。20% 是待标定目标；需检查低等级单位是否被绝对值加成压垮。

淬炼只强化三消附加层，不自动变成酒馆装备强化等级，也不增加 ST 生命上限或技能等级。这样玩家在原生模式仍持有原装备，切换战斗方式不会读到两个互相冲突的强化结果。

### 6.4 素材与获取闭环

首版只设计剧情三消胜利所得的淬炼材料；其余类别待有独立获取玩法和消耗需求时再设计，不照搬王国素材、全套特质石和活动货币：

| 类别 | 获取 | 消耗 |
| --- | --- | --- |
| 淬炼材料 | 剧情三消有效胜利的固定基础奖励；强敌获得较高档，再现不产出 | 武器逐级淬炼 |
| 高档适配材料（后续） | 高威胁剧情战斗的首次有效胜利/预设里程碑 | 高档词缀、萃取/重绑 |

初期只启用剧情三消胜利的淬炼材料与魂片进度；同色学习材料和已学会来源的重复转换均不进入首版。后续若需要重复刷材料，另设计模式或 AIRP 获取口径，再分别校准产消。素材展示使用中立名称和档位；如以后有纯显示别名，映射由宿主控制，不改变机制，也不让 AI 编造掉落。

基础掉落确定性发放为主，少量随机附加用于变化。奖励预算由等级、威胁、有效击败和遭遇来源计算，不让 AI 提交数量，也不根据玩家反复开关页面重抽。普通战中经济能力直接复用原三消引擎，包括生成、消耗、窃取、余额读取、倍率、资源归属与上限，四／五连原生金币收益保持开启。原生武器及全部可达召唤／变形／复制候选适用相同执行规则，不因涉及战中资源而禁用、删段或过滤随机池。正式开战仍检查双方、战场规则和完整派生依赖，检查通过后才创建待完成战斗。战斗内余额与持久奖励分别处理：再现只发未学会魂片；剧情只提交明确的本场奖励；只有实际提交的奖励在结算页显示真实名称和数量。PvP 专用战后收益在对应模式未适配前受限，不能据此关闭普通战中能力。

养成节奏的首轮验收目标：第一场三消剧情胜利有可见学习进度，前 1～2 场剧情三消胜利可进行首次淬炼；已有来源通过往昔再现补齐进度，不要求剧情再次遇到同种敌人。五档来源先按约 20 / 14 / 10 / 7 / 5 次三消有效胜利解锁，高稀有度更快学会，具体场次经实玩标定；混编战可同时推进多种来源，但不额外产出材料。淬炼素材掉落表只按剧情三消胜利的实际频率与逐级成本反推；再现不算作可重复素材收益，不能声称靠再现保证淬炼毕业。

ST 经验、通用币和叙事战利品继续由原冒险体系结算。首版三消报告不额外发 ST 经验或剧情装备，避免同一遭遇领取两份奖励；三消只结算其独立的材料与学习进度。

## 7. 数值与两种战斗方式的切换

### 7.1 两边共享什么

共享角色身份引用、等级、基础属性锚点、已穿戴叙事装备、当前 HP、临时 HP和遭遇身份。同伴三消颜色持久化于酒馆侧角色变量；颜色、淬炼、主动能力配方及独立材料的机制只属于三消附加层。

ST 的“战斗数值模式”当前用于经典/新版伤害计算，不能拿它充当“DND/三消”开关。新增桥接自己的 activeCombat.mode；同一遭遇只能有一个模式持有战斗锁。

共享角色状态是首版的“无缝”；并不承诺两种规则下逐次攻击、动作数和胜率相同，也不把三消能力自动兑换成 AIRP 技能。以后如果希望成长在两种模式同时生效，需要另立明确的双模式能力规则，不能靠 AI 自行理解。

### 三消难度与血量倍率（2026-10-25 用户确认）

三消难度与血量倍率分别设置，独立于 AIRP 的难度及敌人分档倍率。难度后续考虑普通、困难两档，且两档均有动态难度；具体算法、倍率与界面暂不设计，本轮先跑通基础游玩链路。当前运行时 AI 只提交敌人语义需求，不填写难度标签、倍率或叙事权重；程序暂用基础倍率 1。往昔再现继续读取原场冻结配置。

个体面板浮动（2026-10-25 用户确认）：新剧情遭遇的生命、攻击、护甲、魔力四项均由程序独立随机上浮或下浮 5%～10%，取整并遵守既有上下限。浮动在组装阶段完成，实际值保存到本场配置；刷新、恢复、重复打开和往昔再现保持一致。AI 不提供浮动参数；不在本轮扩展难度系统。旧配置继续保留原值。

### 7.2 基础面板

采用独立、版本化的通用转换配置，不调用现有 meta 的 buildPlayerSnapshots() 或原生敌人王国池。

输入优先读取辅助脚本已经算好的生命上限、当前生命、AC、战斗属性/武器面板、六维、等级和经典/新版数值模式；不重复叠加装备加成。攻击基准使用伤害骰期望、等级系数和固定伤害，以及当前模式实际适用的普攻倍率、攻击次数与减伤规则。不能只用“武器等级”代替已有的完整面板，也不能把两种伤害模式用同一个公式处理。

hp、attack、armor、magic 使用一组全局系数和预算曲线转换。HP 与护甲基准共同决定耐久，避免同时满额映射 DND HP和 AC 导致有效生命翻倍；首版优先校准生存与伤害比例，再标定棋盘充能和连消节奏。

现有快照校验的生命上限为 9999，攻击/护甲/法强上限为 999。标定时必须覆盖高等级与高威胁档，不能逐个敌人强行截到上限导致成长失真。超界时要么统一调整该版本双方共用的缩放曲线，要么先在兼容变更中扩展数值域；本场内不临时改变系数。

敌人等级和威胁来自叙事区域与对象实力，程序按同一规则集生成基准；必要时请求抽象耐久倾向，而不要求 AI 输出种族或完整六维。等级不绑定玩家等级，玩家回到低级区域仍面对低级敌人。

### 7.3 HP 回写

入场时 stats.hp 表示三消生命上限，initialHp 表示当前生命，两者不能混用。ST 当前 HP/最大 HP 的比例在入场时保留。

退出时用三消终态生命比例换算回本场冻结的 ST 生命上限；同一规则集下，未行动直接退出和满血正常退出都不改变 HP。临时增加的最大生命不会写入 ST 永久上限；临时护甲、攻击和法强不写回 ST。

ST 临时 HP 需要独立的桥接吸收池：受到生命伤害时先消耗，普通治疗不补回，结果单独回写剩余额。它不能伪装成会受技能修复的普通护甲。这个池是待新增能力；临时 HP 非零的战斗只有在它实现并通过回归后才开放正式同步。

战斗结束且 hp=0 先报告“失去战斗能力”，不自动删除同行者或宣布永久死亡。战斗内恢复/复活只在实际触发时改变结果；永久死亡、俘虏和剧情后果交给酒馆原规则处理。

### 7.4 切换时机

剧情遭遇只支持逐场选择战斗方式。本场进入三消后，AIRP 停止掷骰和扣血；提交结算后再释放战斗锁，下一场可以换回 DND。往昔再现是前端养成挑战而非剧情遭遇，不接管 AIRP 战斗锁，也不改变酒馆角色 HP 或故事进度。

关闭页面保留未完成战斗。玩家可恢复；也可明确放弃，按最后已持久化状态记录中止，无胜利奖励；剧情遭遇的后续交由故事处理，再现只返回图鉴。原场观看重放仅用于回顾，不再次掉落；从图鉴发起的新一次再现才是可结算的新挑战。剧情改写需要新建聊天分支，不隐式把已经结算的战斗倒带。

ST 状态在战斗期间被别的脚本修改时，回写先检查被冻结的相关字段与修订号。冲突则保留结果并提示处理，不直接覆盖新状态。不能假设跨 origin 的 IndexedDB 和 ST 变量存在一个数据库事务。

## 8. 立绘：成图五形态与三视觉维度检索

已有离线标注、资源校验及本地组装预览、蓝图选图与战斗资源接入基础，历史整理记录见 [立绘形态标注](portrait-forms.md)。本文现要求按 rank/form/role 三个视觉维度选图；该规则在查询、生成数据和运行时中的实现一致性仍需核验。完整敌人行为覆盖、预算标定及真实酒馆接线仍按 STATUS 推进。

### 8.1 本轮已完成的资源整理

1800 张现有部队立绘均经过缩略图查看，原类人候选另做面部专项复查，累计 90 项放大复核。标签按成图主体归为人形 803、野兽 197、类人 468、怪物 243、异形体 89。图片记录保存内容哈希、形态、核对方式和依据，原始提示词只作为离线来源证据。

原提示词 1790 个名称、3580 条记录可为 1798 条部队建立来源候选；两条缺源也已直接查看图片归类。同名的游侠、九头蛇按各自文件处理；同内容的六组立绘保持相同形态。源名称写着兽族，不代表成图具有兽面。

本轮为粗粒度形态首轮归类，不声称逐张检查所有细节。新增或内容变化的图片必须重新归类；不能按原种族名自动分配类人。

### 8.2 三个视觉维度严格匹配，颜色独立配置

立绘索引的稀有度来自 rarityIdx 映射，职责标签来自原 role，形态来自本次视觉标注。选图时只按 rank/form/role 三个视觉维度严格相交，manaColors 独立用于机械配置。筛选完成后才按图片内容去重，保留共图资源各自的档位、形态与职责归属。此处的立绘职责标签仍约束选图；配方职责由 4.4 的实际机制签名验证，配方来源和图片来源可分别绑定。旧画像保存的 query 中若含颜色，该颜色仅用于历史记录与原绑定的一致性验证，不参与新选图或换图筛选；恢复时复用已保存的真实图片绑定。

availability 应按 rank/form/role 导出有图组合及数量，保留这三个视觉维度的组合约束，不导出源名称、种族、王国和提示词。旧版按源颜色拆分的组合统计仅作历史数据，2026-10-25 实测索引含 1800 条、1794 张独立图片、199 个 rank/form/role 有图组合；有图组合与机械配方可用性分别校验，职责与颜色的组合仍以实际编译结果为准。

### 8.3 后续前端选图与持久绑定

已登记蓝图有固定立绘 → 复用绑定
新蓝图 → rank/form/role 三视觉维度合法性检查 → 三者严格相交 → 对相同图片去重
       → 候选非空：用独立 visualSeed 选择并保存

既有本地组装预览提供真实候选、持久化蓝图选图及兼容换图时保留技能与数值的基础；三视觉维度已通过本地跨颜色换图、保存与重载测试；真实酒馆准备流程仍需验证。visualSeed 应独立于战斗 RNG；同一蓝图再次出现复用图片。图像加载失败在同一 rank/form/role 候选池内尝试其他实际图片，保留三个视觉维度的约束；法力配置仍由机械组装流程校验。

### 8.4 与后续敌人组装器的衔接

本地预览台已有候选数量、真实立绘以及主动／特质机制说明；按 rank/form/role 选图与法力颜色独立配置已通过本地回归，完整预算与族群关系标定继续推进。形态不自动授予抗性，立绘不自动继承源技能；职责的实际效果由技能规则校验。

族群身份与形态分别保存，关系代码用于同族连续性。前端选中某张西幻图，不把它原来的具体种族、职业、名字、物件和跑图文本发送给酒馆 AI。

## 9. 战报：保留完整过程，再生成可读投影

### 9.1 必须记录的事实

初始基础为 BattleSession 事件流与 BattleResult 终态及摘要；现已接入剧情战果的击败、倒下／复起、初末生命与净损耗报告，并支持生命及事实回传。本地报告和真实酒馆验证分别记录，逐行动／选择的中断恢复仍待完成；eventSummary 不作为完整战报的替代。

本地保存每次已接受的行动及其因果事件：谁行动、目标、实际 HP/护甲变化、状态施加/抵抗/解除、恢复、额外行动、召唤、变形、撤退与失去战斗能力。召唤对象使用派生 unitRef，并记录来源和寿命，不向酒馆暴露 troopId 或原始部队名。

每场剧情三消和再现另保存一份玩家可读的战果明细，直接来自引擎终态和行动记录：

- 本场胜利、败北、撤退或中止，以及实际达到的胜负条件。
- 每名敌人是否被击败、是否曾复活及其结束状态；召唤物单独标明，区别于原始阵容的魂片来源。
- 每名我方参战者是否曾倒下、是否实际复活、结束时能否继续战斗；倒下后复活仍保留曾倒下的事实。
- 各参战者入场/结束 HP、对应生命上限、生命百分比及净变化，临时 HP 单列。例如 80% → 35% 表示净减少 45 个百分点；战中累计受伤与治疗另按行动保存，不把累计伤害当作结束时净损失。

结算页展示以上战果，剧情三消报告回传相同明细供酒馆续写；再现明细只进入本地战报，不把练习中的倒下或受伤同步成剧情事实。

现有事件中部分状态/增益没有施加者、部分伤害 amount 未必等于 HP 实际扣减；实现要在会话行动边界补充来源和前后快照，记录真实变化。不能在报告阶段猜测“是谁导致了这次状态”。

### 9.2 面向 AI 的输出

提供三个读取层次：

1. 默认上下文：三消胜负、敌方击败名单、我方倒下/复活情况、各参战者入场到结束的生命百分比及净变化、每个对象的终态、结算，以及按行动顺序排列的机械过程报告。
2. 逐行动中立报告：玩家可直接展开/导出；完整因果信息均可回指，不丢失状态抵抗、复活和关键变化。
3. 底层棋盘与事件日志：本地保存，用于重放和排查；不自动塞给模型。

正常短战斗默认回传全部有意义的行动记录。长战斗按行动区间分块保存；默认报告明确列出覆盖范围并保留所有伤亡、状态和关键效果，其他块可由宿主加载或玩家导出。没有额外读取工具时，必须提供“完整发送/分段发送”的用户操作，不能谎称 AI 已经看完被截掉的日志。

投影使用 unitRef、动作编号、目标、效果类别与真实数值；族群联动可引用已声明的族群关系。内部技能名称、原王国/种族名、文件名、原特质名称和原始日志错误不进入提示词；法力六色可作为机械信息，但不附会为世界观元素。AI 只能给事实添加叙事表达，不能改胜负、复活对象或重新决定掉落。

状态翻译必须保留具体机制，例如“无法普攻”“无法主动施法”“持续生命损失”，不能把几种不同控制统一成模糊的“被控制”。颜色转换在叙事报告里可表达为“调整自身充能、获得后续主动机会”等中立机械信息，具体棋盘坐标与色名留在完整技术日志。

## 10. 浏览器存档与酒馆接入

### 10.1 存储权归宿主

IndexedDB 放在酒馆端桥接运行的 origin 下；它保存队伍配置、装备实例绑定、蓝图、能力、魂片、材料、淬炼、战斗票、日志、结算账本和待同步队列。战斗 iframe 收到冻结请求后只负责执行，不拥有独立的一份长期养成真值。

这样 iframe 地址可以是静态站点或 localhost，不需要第三方 iframe 的 IndexedDB 作为唯一存档来源。若使用的酒馆插件环境实际上只允许脚本在另一个 iframe 中运行，则不能声称它拥有 ST origin 的存储；第一期必须在真实环境验证，并调整为宿主扩展或宿主提供的存储 API。

本地存档管理器总共最多保留 3 个槽位，一个槽位唯一绑定一份酒馆聊天，一份聊天也只对应一个槽位。三个槽位分别服务至多三个聊天，不在同一聊天下轮换三套养成进度。聊天级变量保存其绑定存档 ID，同伴颜色落在酒馆侧对应角色变量，宿主 IndexedDB 保存对应聊天的完整图鉴、魂片、能力、材料、战斗和结算数据；加载时校验宿主实例与稳定聊天 ID，不按角色卡名或聊天显示名称识别。

切换回已绑定聊天时加载原存档；切换到未绑定聊天时须创建新的独立空档，占用一个空槽。满 3 档后停留在存档管理页，由玩家手动删除一个旧档再创建；不自动清理、不把已有槽位直接换绑成另一个聊天，也不把旧档进度复制过去。删除前明确显示绑定聊天、进度和删除范围，由玩家确认；可先导出备份。删除只移除该槽位的三消存档并解除绑定，不删除酒馆聊天正文或原有 AIRP 角色变量。原聊天再次启用三消时按未绑定聊天创建新档，或从其专属备份恢复。

切换聊天前持久化当前战斗/结算；未结束的战斗、结算和待同步报告始终归属原聊天存档，回来后继续，不投递到新聊天。从历史消息建立新分支或复制聊天时，只要宿主生成了新聊天 ID，就按新聊天创建新档，同样占用三个名额之一；复制来的旧绑定引用需清除，不自动继承原图鉴或魂片。仍使用原聊天 ID 的历史编辑不自动倒带三消进度；要重开则手动删除并新建该聊天存档。

提供存档列表、绑定聊天标记、手动删除与逐档导入/导出 JSON；导入用来恢复对应聊天的存档，遵守一聊天一档和总量三档上限，不与其他聊天合并进度。聊天变量引用丢失时，可按已校验的同一聊天 ID 找回其现有绑定；实际数据已被清除时显示待恢复，不使用其他聊天的槽位顶替。更换浏览器时须同时携带对应聊天与三消存档备份，单独的聊天绑定引用不包含完整养成数据。首版无需云同步。

### 10.2 接入不是一条正则

| 组件 | 实际职责 |
| --- | --- |
| 正则/消息渲染钩子 | 识别独立协议块，渲染折叠入口，保留原始数据 |
| 酒馆桥接脚本或扩展 | 读取当前卡变量、保存本地档、锁定本场、发送冻结请求、处理回执与结果、更新变量、注入报告 |
| iframe 战斗页 | 就绪握手、显示准备与战斗、执行引擎、回传行动和结果 |
| AI 提示词 | 教会抽象设计规则、引用规则和等待结果规则；不执行发奖或存档 |

现有 postMessage 桥可以复用 ready/start/result/ack。仍要补充准备配置交换、逐行动持久化、恢复会话和中立报告；这些是新增工作，不是已有桥接自动附带的功能。

部署地址与实际 ST origin 需要明确绑定，复用现有来源校验。启动自检验证变量可读、通信可用、存档可写、报告可插入；失败留在准备页给出具体操作，不进入“战斗打完才发现不能回传”的状态。

### 10.3 受理、恢复与结算

状态机：待准备 → 已冻结 → 战斗中 → 结果已保存 → 等待 ST 同步 → 已完成。另有校验失败、中止和同步冲突状态。

每次接受行动后，把种子、冻结快照、规则/内容版本、行动序列和相关事件增量发送到宿主持久化；持久化回执后才允许接受下一行动。页面重开时按已确认序列复现，不重抽技能或棋盘。更新版本不能直接用新规则回放旧战斗；优先保持已打开会话版本，已结束结果永远读取原存档。

逐行动日志需要覆盖投降、中止和其他改变状态的入口，不能只保存普通交换/施法。回放从冻结请求与初始种子重新创建会话，再执行已确认行动；不能从恢复时的界面重新运行一次敌人设计器或重新计算装备绑定。

结算按本场稳定 ID 只提交一次。ST 补丁与报告进入待同步队列，宿主写入完成再确认；重试不再次加材料、加魂片或扣 HP。ST 变量写回和同步标记应通过同一宿主更新完成；若插件做不到，写回使用带基线校验的绝对终态值和可恢复收据，不用可重复执行的 HP 增减。

原生 meta 使用原目录、王国池与成长；通用入口不调用这些固定编队路径。两个入口共用执行器、效果原语和已有战斗 UI 组件，不各复制一套技能库。新机制优先增加通用效果能力，再分别配置两个模式的数据。

## 12. 分期交付与验收

当前先完成立绘五形态与 rank/form/role 三视觉维度筛选，随后建立特质/技能规则与敌人预览台，再接真实宿主闭环和养成。最小宿主通信探针可以在数据准备时独立验证，但不能用无立绘占位战斗当作产品交付。每期的交付必须可以单独试玩或查验。

| 阶段 | 交付内容 | 通过条件 |
| --- | --- | --- |
| P0：语义规则与数据底座 | 五稀有度/既有九职责/五形态/法力颜色词表；rank/form/role 三视觉维度立绘查询与独立法力配置；33 类原标签依赖盘点；全量技能适配索引；提示词解析和资源关联、语义归类、图片抽检与候选统计 | 每类选择有明确影响；职责有核心能力签名；公开词表不含具体物件或源世界身份；提示词/文件可追溯；同名改名与缺失有处理结论；开放形态有真实图片；同族机制有绑定方案 |
| P1：敌人组装器 | 语义分类驱动的预览台；支持各稀有度至少 90% 适用敌人的能力适配；真实卡片与 4 人队预览；单体/全队预算和所需上下文绑定 | 各原始稀有度与通用五档分别达到 90% 覆盖；特殊机制排除与普通缺口逐条可查；相同输入保留预期职责；正式敌人有实际图片；关系匹配正确；相同种子复现 |
| P2：战斗闭环试玩版 | 最多 4 人固定同行队伍；武器实例首次绑定；准备页/完整战斗/本场结算；逐行动报告；HP与临时HP；中断恢复与同步队列；一聊天一档与总量三档限制；保存剧情三消快照与战果明细 | 同角色跨两种战斗方式保留状态；无双重算伤害；刷新不丢已确认行动；胜败、撤退和重试账实一致；击败名单、倒下/复活和生命百分比变化有据可查；第 4 个聊天须手动删档后创建；P3 只读取实际三消胜利记录解锁 |
| P3：养成闭环 | 持久蓝图、三消胜利后解锁的魂片图鉴与整场往昔再现、同色技能替换、武器淬炼、独立养成页、逐档导出导入 | 按稀有度约 20 / 14 / 10 / 7 / 5 场解锁；同场同源仅 +1，混编战逐源推进；相同能力任一来源学会即全部视为已学会，整场均学会后关闭挑战；再现只给未学会能力的魂片，观看重放不发奖；不改 ST HP/剧情或重复发首胜；不同源的学习点数不因职责相似合并；不同聊天不串档；结算显示所有实际增量 |

P1 按第 4.5 节逐档验收；配方数量随覆盖需要确定。达到 90% 所需的棋盘机制、召唤、变形、族群关系及复杂条件在 P1 完成适配，P4 承接达标后的剩余缺口与新增扩展。覆盖报告始终分列总量、明确特殊机制排除项和普通适配缺口。

### 每期共同验收

- 设计语义：档位、职责、剧情权重、形态各有明确规则；实际效果符合职责签名；内部随机不能改掉主要设计意图。
- 世界观隔离：提示词的有意义通用分类、校验错误、武器摘要、战报和同步信息不泄漏原始世界标签；换图不改变战斗逻辑。
- 立绘与族群：rank/form/role 合法视觉组合可解析真实资源；验证改变法力颜色不影响新选图候选，旧画像 query 的颜色仅作历史记录验证，机械配色继续独立校验；实际图片符合已确认标签；族群与图片不一对一锁死；同族联动、克制和异族排除按声明关系生效。
- 数值标定：覆盖 1/10/20/49/50/95 等等级、经典/新版面板、残血、临时 HP、不同 AC 和武器档；验证排序与成长连续，不硬设所有场景同胜率。
- 战术组合：至少覆盖高频输出、蓄力输出、前排承伤、控制、恢复、资源支援和常见互相联动；专测无限控制/额外回合循环与过量恢复。
- 结算：背包实际增量、账本、结算卡和报告一致；败北、未掉落、逃离、重复消息、旧消息重渲染都不伪造奖励。
- 存档：正常关闭、强制刷新、断开通信、多标签页、逐档导入导出、聊天切换、新分支新建、三档满额后手动删除和规则版本变更都有明确结果；复制聊天不沿用旧绑定。

### 当前编队实现与资源复用边界（2026-10-23）

组装预览现支持 1～4 个有序敌人、重复来源的独立配置、站位调整、移除及整队保存恢复。保存包含完整蓝图和规则版本；任一成员损坏时整体提示重组。基础面板直接加总实际开战前数值，各位置单独充能，共享颜色与环境召唤均值可见。这些数据只说明配置事实，整队强度、职责联动及武器关系仍待实战标定，逐敌人完整覆盖不因此增加。

经济设计复核保留两类事实：战斗内资源生成／支出／转移／余额，以及本场实际写入存档的持久奖励。前者直接复用原引擎执行，后者沿用本书奖励边界。纯战后收益机制的原有奖励价值与再现只魂片之间存在待决冲突；本段记录缺口，不定义新的兑换或持久币，也不将失效计数视为已完整适配。普通战中能力不再增设经济门禁；PvP 专用战后结算仍需对应模式的执行及独立验收证据。见 [ST-04 审查记录](sillytavern-st04-review.md)。

当前战斗内资源账本已实现并通过本地集成回归，Schrodinger 已独立签收账本基础切片。该可选结果字段记录开局和最终余额、触发方、来源、实际收支、上限／倍率及窃取关联，导出／恢复时对账；结算页以独立“战斗资源记录”展示。实际奖励卡仍只读本次已提交的 grants，记录余额本身不构成持久奖励。剧情回写兼容新账本与旧结果；普通战中资源机制恢复原生执行；纯战后收益仍按适用模式处理。逐敌人覆盖继续以完整行为验收为准。
