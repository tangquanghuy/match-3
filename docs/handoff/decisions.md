# 需求澄清过程与最终执行口径

基准：2026-10-28。本文是对原话的产品解释，逐条原文在 [用户逐轮归档](user-dialogue.md)，原始目标见 [交接正文](README.md)。后文“当前实现”只描述现有文件及状态记录，独立于用户是否最终验收。

## 一、最初接入目标：让三消承担文字跑团的真实战斗

[U001–U002](user-dialogue.md#u001) 先要求清理无用文件、过时设计和已结束的技能审核记录。这是酒馆接入前的项目背景，保留在完整原文中；不据此推断当前接入任务已经完成。

[U003](user-dialogue.md#u003) 首次给出完整链路：运行时 AI 在正文中输出模组文本，外部正则换成远端网页，嵌入酒馆，按敌人参数开战，战报返回 AI 演绎。玩家存档倾向浏览器本地游客模式。后续所有任务都应服务这条实际游玩链路。

[U004](user-dialogue.md#u004) 要求先研究数值和养成衔接：酒馆等级与现有面板、武器淬炼、材料、固定队友、灵魂碎片、海量技能如何提供给 AI，以及同一仓库持续维护。[U005](user-dialogue.md#u005) 明确纠正：酒馆技能树/资源技能/特质属于 AIRP，三消使用独立附加能力，借变量、装备代码和前端桥接。

接手口径：共享角色身份、等级和必要生命状态，通过附加层保存三消颜色、能力及武器绑定。研究武器/部队实际规则再设计映射；不要把 AIRP 原技能名或技能树强行当作三消技能。

## 二、通用敌人设计：语义抽象、真实图片和世界观隔离

[U006–U010](user-dialogue.md#u006) 连续追问：名称、职业、种族、立绘、技能怎样对上；只声称按“亡灵、人形、重甲、面具”检索不构成可执行方案。西幻资源可近似借用，但暴露给运行时 AI 的机械标签应避免污染中式、日式等世界观。

[U012–U015](user-dialogue.md#u012) 纠正两个方向：继续使用真实图片，抽象图形方案作废；标签应对 AI 有语义，避免全是无含义代码，也不要从跑图提示词细抠火器、宽檐帽等小外观标签。[U014](user-dialogue.md#u014) 提供历史立绘提示词作为打标参考，不意味着恢复精细服饰检索。

形态分类的演变：

| 原话 | 当时要求 | 最终采用 |
| --- | --- | --- |
| [U016](user-dialogue.md#u016) | 人形、野兽、类人、怪物四类 | 被下一轮扩展。 |
| [U017](user-dialogue.md#u017) | 加入异形体，共五类；档位杂兵、精锐、首领、领主、传奇 | 五形态和五档保留。原句的颜色绑定见下文修订。 |
| [U018](user-dialogue.md#u018) | 有兽耳兽尾但仍是人脸归人形；类人没有人脸 | 按实际外形判断，种族文本不决定图片分类。 |
| [U027–U030](user-dialogue.md#u027) | 再次确认首版不用“亡灵、重甲、面具”这样细分 | 精细语义检索不列为待定首版要求。 |

[U017](user-dialogue.md#u017) 曾要求“法力颜色、稀有度、形态、队伍职责，共同确定一张立绘”；[U078](user-dialogue.md#u078) 后来明确纠正“立绘怎么可能是跟颜色绑定”。因此当前以最后一次纠正为准：颜色是实例机械配置，不参与选图。现有 v2 图片优先 rank/form/role，缺视觉职责时回退同 rank/form；这是实现策略，机械主职责仍由源池保证。

[U010](user-dialogue.md#u010) 早期反对把叙事文字交给组装器；[U081](user-dialogue.md#u081) 后来要求战斗块也包含姓名和种族，供引擎渲染。最终姓名和种族作为显示身份进入协议，程序无需接收整段叙事或固定原生世界观身份。此修订覆盖早期“名字只留正文”的描述。

## 三、最小协议：程序承担内部状态，AI 只完成明确任务

[U019–U021](user-dialogue.md#u019) 质疑协议示例里的 `unitRef/blueprintRef`；[U022–U023](user-dialogue.md#u022) 要求原始需求及后续澄清都保留原话。这正是本次完整归档的依据。

[U059–U064](user-dialogue.md#u059) 进一步修订运行时协议与提示词：

| 被指出的问题 | 最终边界 |
| --- | --- |
| 大段机制保证、随机分支、标签判断说明，缺少什么时候做什么的任务 | 以触发判断、战前配置、输出等待、接收战报四阶段组织。 |
| 固定 `assembly:"classified"` 还让 AI 填 | 常量与内部版本由程序补齐。 |
| AI 核对 battleId/requestId、读历史镜像和奖励收据 | 程序选择和投递本场真实战报，AI 接收后续写。 |
| 让 AI 自己读看不到的模式变量 | EJS 读取当前 MVU 并控制规则注入，沿用已有 AIRP 规则模板方式。 |
| version/difficulty/storyWeight/requirement 等字段 | 当前运行时入口省去这些内部字段和独立设置项。 |

[U080](user-dialogue.md#u080) 把 `[match3]` 改成 `<match3>`，要求正则同步。[U081](user-dialogue.md#u081) 增加姓名和种族。当前文件定义顶层只交 `enemyDesigns`，每名敌人七项：

```text
name       当前剧情姓名或称呼
race       当前世界观种族名
rank       杂兵 / 精锐 / 首领 / 领主 / 传奇
level      1～100 整数
form       人形 / 野兽 / 类人 / 怪物 / 异形体
role       Defender / Striker / Generator / Support / Mage /
           Warlock / Assassin / Warrior / Warmaster
manaColors Red / Blue / Green / Yellow / Purple / Brown 的不重复集合
```

以上枚举、等级上限、1～4 敌人和队形细则来自当前实现/提示词，不都出自逐字用户定义。完整安装内容直接使用 [运行时 AI 提示词](../sillytavern-runtime-ai-prompt.md)，程序和文档对照 [协议说明](../sillytavern-runtime-ai.md)。避免从本交接正文另外复制一套不完整提示词。

[U079](user-dialogue.md#u079) 明确指出 32 KiB 对运行时 AI 没有任务意义。字节限制留在程序输入校验，不再放进 AI 工作说明。代码层字段、幂等 ID 与数据约束仍可存在，不应把它们变成 AI 的设计负担。

## 四、敌人组装器：从少量配方和逐条核对转向分类规则

[U043](user-dialogue.md#u043) 否定 24～40 个配方的首版目标，要求包含每个稀有度至少 90% 的敌人；晋升度、淘宝模式、魔头等特殊依赖可以不组装，但需要明确分类依据。[U050–U054](user-dialogue.md#u050) 指出关键进度没有推进、反复造已有引擎功能、逐个手工核对约 1800 个敌人偏离目标。分类组装和分类验证是主线。

[U069–U072](user-dialogue.md#u069) 追问具体可执行设计：效果组合数量与长度、低阶复杂度、吞噬/额外回合等强力机制的权重、职责相关性、单体/全体/溅射/散射伤害、爆破颜色与数量、召唤/变形对象、造石供魔转色对象、技能基础值/费用/魔力或 HP/护甲系数。保留完整技能语义及数值关系后，程序才能组装和验证。

[U073–U074](user-dialogue.md#u073) 指出“输出 99.4%、法师 100%”说明统计或分类错误。附带伤害不等于输出主职责，用魔力系数不等于法师主职责。供魔、辅助、坦克可以有伤害，不能因此串到输出池。

[U075](user-dialogue.md#u075) 最终分工：运行时 AI 选择 role 等基础信息，组装器按权重选择和组合效果。现有 v2 实现采用源主职责固定分池，按战法分组后选完整原生主动，再组独立有序特质，保留费用、公式、固定产色、条件与分支。这是对复杂真实技能的实现办法；不把几个抽象 effects 标签拼成简化伪技能。

[U076–U079](user-dialogue.md#u076) 要求子 agent 只看实际提示词生成战斗块，再用现有组装器进行整队模拟，并对提示词本身提出意见。盲审不能预先塞候选表或修补答案后冒充原始输入。完整规则、种子、失败样本、保存恢复、真实战场结果需留存。按机制族验证与覆盖不是“无需行为测试”的同义词。

接手阅读：[设计准则](../sillytavern-enemy-design-guidelines.md) → [分类组装规则](../sillytavern-enemy-assembly-rules.md) → [v2 修复与盲审](../sillytavern-enemy-assembler-v2.md) → [自动覆盖报告](../sillytavern-enemy-assembly-coverage.md)。旧逐来源审查仅作历史回归证据。

## 五、魂片、图鉴、再现和多聊天存档

[U033–U040](user-dialogue.md#u033) 收敛以下规则：

| 主题 | 用户确认 | 当前产品实现补充 |
| --- | --- | --- |
| AIRP 刷取 | 前端做往昔再现，避免为魂片反复演同一遭遇。 | 独立再现战场和独立满血我方快照，不产生新的剧情战果。 |
| 图鉴 | 只有三消胜利才进入。 | 记录实际有效击败来源，保存原整场敌方配置；失败和 AIRP 胜利不新增剧情图鉴。 |
| 学习耗时 | 低稀有度大约二十来场，高稀有度四五场。 | 当前五档基线 20/14/10/7/5；中间档和精确值属于待体验标定方案。 |
| 停止刷取 | 学会能力后不再重复刷；未来刷材料另设模式。 | 同能力来源一起标记学会；整场全部学会后关闭挑战。混编仍有未学来源时重打完整原阵容，只结算有效未学来源。 |
| 来源与能力 | 不同来源出现同一能力，视为已经学会。 | 按能力身份去重，按未学来源累计；同来源多只每场最多 +1。具体 ID/hash 是程序实现。 |
| 暂无使用者 | 魂片可以先收藏，没有兼容同伴不影响获取。 | 收藏、学习和颜色兼容装配分别判断。 |
| 槽位 | 一个槽位绑定一个聊天，最多三个；第四个手动删除。 | 绑定稳定聊天身份、导入校验、账号隔离等属于程序职责，仍需真实复杂环境验收。 |
| 同伴颜色 | 写回酒馆侧变量。 | 初次生成后持久化，刷新和描述变化沿用原值。 |
| 无武器 | 从现有最低稀有度武器选默认武器。 | 当前选 Common 骑士之剑 `gw_KnightsSword`，蓝色、3 法力。武器具体选择是实现决定，无需向叙事背包追加道具。 |

现有产品书把再现产物限制为未学能力魂片，不产通用材料或叙事奖励；剧情胜利的材料和淬炼仍需完成产品闭环。再现的原始配置、规则/能力版本封存与代码升级后的精确复现是持续验收项。保存开局蓝图尚不自动等于跨版本完整可重现。

## 六、数值桥接和动态难度的边界

[U065–U068](user-dialogue.md#u065) 确认三消难度与血量倍率分开，未来考虑普通/困难且各有动态难度，但当前先跑基础链路。HP、攻击、护甲、魔力浮动由程序负责。AI 不额外填写每个数值维度。

现有实现采用确定性随机波动并冻结每场结果；文档中的 ±5～10% 是当前实现幅度，不是用户指定的长期平衡要求。淬炼基础面板增量建议封顶 20%、前 1～2 场可首次淬炼等属于体验目标或设计建议，需真实试玩验证，不列成“用户已确认数值”。

用户要求记录真实生命受损百分比，不等于要求结算页堆一份生命技术报表。HP、倒下/复起事实应存在战报与收据；原生结算页以玩家可用的奖励和结果呈现为准。

## 七、宿主入口、页面复用及交付标准

[U047](user-dialogue.md#u047) 要求继续推进并由子 agent 验收直到可交付人工测试；[U056](user-dialogue.md#u056) 明确人工测试的前提是发布网页后到真实酒馆联调，嵌入页面及全屏链路要可用。夹具、独立调试页和公开预览分别记实际证据。

[U057–U058](user-dialogue.md#u057) 给出真实角色卡入口：开局页维护模式开关，底部状态栏唤起单独注入的管理网页，参照已有外置状态栏。存档创建不应依赖额外独立助手脚本。当前可选兼容加载器和独立三消 IIFE 包装都不等于正式角色卡必装脚本。

[U082–U090](user-dialogue.md#u082) 连续纠正页面实现：

- 正则替换后的页面须在酒馆助手环境真实可渲染；源码本地可开不是足够证据。
- 复用原三消战前加载、详情、战场、战后结算和美术，独立管理页也沿用原项目风格与工作区。
- 管理按钮从底栏打开；开战流程不增加另一层管理面板或多余中转。
- 删除“剧情三消战斗”“即将开战”“结束后保存结果”等用户没有用途的提示，避免重复全屏、返回存档和额外贴片。
- 名字、种族、等级进入原有详情与正常身份显示；内部公式、哈希指纹及测试角色名不成为玩家界面正文。

[U091–U094](user-dialogue.md#u091) 最后指出重渲染直接显示胜利、结算布局和魂片奖励名称错误。当前修复方向是按持久状态展示入口、显式打开旧收据、重渲染收起旧结算，继续复用原生结果页；魂片按原遭遇敌人身份命名。原话未详细指定最终名称句式，现有“敌人名的灵魂碎片”属于修复方案，尚待实际人工体验确认。

## 八、明确留在后续或需要证据的内容

| 项目 | 当前归属 |
| --- | --- |
| 普通/困难与动态难度 | 用户明确暂缓。保留难度和 HP 倍率独立，不扩成当前协议负担。 |
| 学会后反复刷材料 | 用户明确暂不考虑；未来单独模式或 AIRP 获取另行设计。 |
| 萃取、重绑、复杂材料体系 | 产品书列后续；当前先完成武器绑定、剧情材料、淬炼与存档。 |
| 族群/王国专属叙事映射 | 通用机械适配可研究；首版协议不强制暴露固定世界观。 |
| 临时 HP、逐行动恢复、跨版本完整技能封存 | 现有任务中仍有缺口，继续实现和验证。 |
| 所有组合平衡与全量机制行为 | 结构覆盖和小批种子模拟之外另验；保留失败样本和真实分母。 |
| 最终 UI 满意、真实模型自动出块全流程、完整养成与备份恢复 | 以人工真实酒馆证据和验收结论收口。当前尚未完成整版验收。 |

## 九、旧文件出现冲突时怎样处理

| 可能看到的旧说法 | 接手时以何者为准 |
| --- | --- |
| 任务书里“四维精确选图失败”仍写作当前阻塞 | 该失败样本保留；后续解绑颜色和 v2 盲样通过是最新切片结论。ST-04 总任务仍进行中。 |
| 产品书 §2/§3 仍说名字不进协议、管理可从战斗准备卡打开 | 姓名/种族七字段及独立底栏管理页的后续原话、当前提示词和页面实现优先。 |
| 产品书写结算页固定展示生命报表、无奖励加提示 | 原生结算复用和后续删除废话的要求优先；事实保存在收据/战报，不额外发明结果报表。 |
| 旧提示词说明表仍称“五项” | 当前每敌人七项是五个机械字段加姓名和种族；直接使用当前提示词与解析器。 |
| README 说暂无任务或计划待开始 | 本次导航已修正；执行任务和未完成范围看 STATUS 顶部最新结论。 |
| 历史 release 或 zip 里的网页版本 | 只代表当时产物。当前源码、重新构建、已安装角色卡、线上模块分别核对。 |

不要通过删掉历史失败记录制造“早已完成”的印象；也不要把被后续明确纠正的旧设计继续当作待定用户需求。版本事实和用户意图分开保留。

## 交接补充：接手人本地部署

归档原话截止本次交接请求之后，用户补充：“另外在交接文件里，说明一下要怎么本地部署，因为其他接手的人是没有Cloudflare的线上部署权限的”。落实为 [本地部署与真实酒馆联调](local-deployment.md)：提供独立本机静态服务、开局与底栏本地副本、从本机安装页下载正则、现有 MVU/EJS 合并位置和联调验收步骤。公开站发布为可选维护流程，接手人不需要原账号权限。95 条原话归档及原始附件仍保留此前提取边界；本条补充单独记录于此。
