## 4. 每轮节奏（一轮 = 每个验收窗口 1 批 10 项）

1. **领批**：窗口按车道顺序取下一批，在 `lane-<窗口>/round-<nn>.md` 写入 10 个 key。
2. **核对**（验收窗口）：对每项按操作指南 §3–§5 三方对照：英文子句 ↔ 原生 `SpellSteps`（有序、每个参数）↔ 最终注册原型；逐项写真实 `TurnEngine.castSkill` 测试，至少覆盖：双方阵营、该项特有参数、一条负例／条件不满足、低蓝或沉默、有目标死亡或屏障的边界。
3. **分流**：
   - 全部一致 → 用 C1 骨架补全判定，`decision: accept`，写入 `lane-<窗口>/signoff-round-<nn>.json`。
   - 发现差异 → 不改源码，在 `lane-<窗口>/issues.json` 追加（key、子句／步骤、预期 vs 实际、最小复现测试名、疑似层级），该项保持 `draft`。
   - 原版语义不明 → 按 §5 查证；仍无法确定标 `source-dispute`，交 fix 裁定。
4. **自检**：`npx vitest run tests/unit/gowLane<窗口>B<nn>.test.ts` 与 `npx tsc --noEmit` 均通过，才能交；交付后该测试文件冻结。
5. **合并窗口期**（coord，每轮末固定时段，如每 3 小时）：宣布冻结 → 各窗口停写 `tests/` 与 `src/` → C3 合并 → `node scripts/verify-gow-snapshot.mjs` → 重建队列／索引 → C4 看板 → 解冻。凭证失败时本轮只合并通过部分，失败项退回原窗口。
6. **修复**（fix，与验收并行、不在冻结期提交）：按 `issues.json` 排序修复：公共原语 > 组装器 > 数据文案。修复先写失败测试，再修，再反查全部调用方，把受影响且**已签收**的 key 列入 `lane-fix/requeue.json` 交 coord 退回相应车道复核。

## 5. 联网查证规则（1:1 复刻判定用）

- 基线是仓库保存的英文描述与原生 `SpellSteps`；二者一致时以它们为准，不以网络上的新版本改动覆盖快照（范围声明见上位任务书）。
- 仅在以下情况联网：英文与原生步骤冲突；原生步骤语义本身不明（例：`TwoWeakestEnemies` 的“最弱”按生命还是战力、平手顺序；散射分配；召唤池范围）；已有裁定未覆盖的公共规则。
- 优先级：官方（游戏内帮助、官方论坛 / 补丁说明、开发者 Brian 指南）> 社区数据库（Taran's World、gowdb 等）> 社区讨论。社区结论必须标注来源等级。
- 可作签收证据的网页必须保存到 `artifacts/gow-skill-audit/gold-primary-sources/`（由 fix 窗口统一入库，文件名含来源与日期），记录 URL、抓取日期、sha256；不得引用未入库的在线链接作为证据。
- 查不到确证：保持现行实现，记录 `source-dispute`，不臆造算法。
